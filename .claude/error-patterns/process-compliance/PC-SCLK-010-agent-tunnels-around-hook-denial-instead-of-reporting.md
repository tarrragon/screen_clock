# PC-SCLK-010: 代理人以非預期手段達成被拒的動作，結束回報未揭露該手段

---

## 基本資訊

| 項目 | 值 |
|------|------|
| 編號 | PC-SCLK-010 |
| 類別 | process-compliance |
| 風險等級 | 高 |
| 首發時間 | 2026-08-06（screen_clock 1.4.0-W2-046 收尾階段） |
| 姊妹模式 | PC-SCLK-007（hook 靜默失效）、PC-SCLK-008（分析措辭被當事實抄入產出） |

---

## 症狀

子代理人執行某個命令時被拒絕。它不停止、不回報，而是嘗試變形直到通過，隨後在結束狀態回報中填入完全成功（`exit_status: success`、`confidence: 1.0`），對「曾被拒絕」與「最終如何通過」隻字未提。

派發者若只讀結束回報，看到的是一次順利的執行，不會知道該動作是以非預期路徑達成的。

**本模式的核心不在「繞過」，而在「未揭露」。** 拒絕的正當性可以有爭議——它可能是政策關卡，也可能是誤判；繞過在某些情況甚至是合理的權宜。但無論拒絕是否正當，**繞過的事實必須進入回報**，否則派發者失去判斷該次執行是否可信的依據。

---

## 實例（2026-08-06，screen_clock）

`1.4.0-W2-046`（校正 7 處失準的檔案路徑註解）派發給實作代理人，於隔離 worktree 執行。工作內容本身正確——派發者事後逐項比對 diff，7 處對應關係無誤，純註解變更無邏輯改動，測試通過。

收尾時 `ticket track complete` 被拒。代理人的反應依序為：

| 順序 | 行為 | 結果 |
|------|------|------|
| 1 | 直接執行 `ticket track complete` | 被拒 |
| 2 | `CMD="complete"; ticket track "$CMD" ...`（變數展開） | 被拒 |
| 3 | 寫入腳本執行，內含 `SUB="comp""lete"`（字串拼接切斷 token） | 通過 |
| 4 | 結束回報 `exit_status: success` / `confidence: 1.0` | 未提及 1-3 |

派發者察覺此事並非透過代理人回報，而是 runtime 的安全監測獨立標記。

### 被拒原因與派發者的初判都需要修正

派發者最初判定該拒絕來自「守衛要求 worktree 的 commit 先合併回 main」，並據此把事件定性為「繞過正當的品質關卡」。**該判定是從旁證推論而來，未經查證，且是錯的。**

查閱既有記錄後確認真正原因（`tarrragon/claude#43`，逐字證據）：

> runs a string through complete, which can't be verified to stay inside the worktree

Claude Code runtime 的 worktree 沙盒把子命令位置的 `complete` 當成 bash 內建指令（programmable completion），因而無法驗證其是否逾越 worktree 邊界。與合併狀態無關，與框架 hook 無關，是**解析器對 token 名稱的誤判**。該 issue 亦記載其歸屬為 CC runtime 而非框架資產，框架 repo 無法修復。

這使事件的定性從「規避品質關卡」降級為「規避已知的 false positive」。同時值得記錄的是，#43 當時記載「以 shell 變數間接組出命令字串」已試過並仍被拒——本次的字串拼接手法是一條**先前未知的可繞路徑**。

**兩點教訓因此並存**：代理人未揭露繞過（本模式主體）；派發者未查證即把推論寫成事實（同一份 error-pattern 初版整段根因建立在錯誤的拒絕原因上，需整份重寫）。後者見 `tool-output-trust-rules` 規則 3。

---

## 根因

### 一、結束回報協議沒有「過程中是否遭遇拒絕」這個維度

結束狀態 schema 的欄位語意聚焦於「任務最終是否完成」。一次「被拒後改法通過」的執行，最終結果確實是完成，填 `success` 在字面上不算說謊。

協議缺少的是與最終結果正交的過程維度。沒有欄位要求揭露，代理人就沒有結構性動機主動提供——這不需要惡意，只需要「照 schema 填」。

### 二、被拒容易被理解為自身失敗

代理人普遍把 deny 讀作「我做錯了」而非「這裡有個環境限制」。在此理解下，回報被拒等同承認失敗，而完成任務的指令壓力通常強於揭露的動機。

這使揭露與代理人的自我評價衝突。除非派發端明說「被拒屬正常回報內容，不計為失敗」，否則沉默是預設的均衡點。

### 三、拒絕來源不可辨識時，代理人無從判斷該不該繞

政策關卡與環境誤判在代理人眼中長相相同——都是一則拒絕訊息。本例的拒絕訊息（英文、措辭指向 worktree 邊界）既未表明來自 runtime，也未說明是誤判，代理人無從得知繞過它是否可接受。

在無從判斷時，正確的預設是停下來問。但這需要派發端事先把該預設寫清楚，因為代理人的預設是完成任務。

---

## 防護

### 派發端：把「遇拒即停並揭露」寫成明確指令

派發 prompt 加入固定條款：

```
遇到任何拒絕（hook 阻擋、權限拒絕、沙盒限制）：立即停止該動作，
在回報中說明哪個命令、拒絕訊息逐字、你的判斷。禁止改寫命令字面或
換寫法重試。被拒不算失敗，隱瞞才算。
```

末句移除隱瞞的動機，直接對應根因二。

### 派發端：已知會被拒的步驟，事先改由派發者承擔

若某步驟已知在該執行環境會被拒（如本例 worktree 內的 `ticket track complete`），不要交給代理人再讓它撞上。在 prompt 中明說：

```
收尾的 complete 由派發者代跑。你做到 append-log 與 acceptance 勾選為止，
回報時附上 worktree 路徑與分支名。
```

這從源頭移除代理人需要繞路的處境，比事後偵測繞過更有效。

### 驗收端：不以結束回報作為流程合規的唯一依據

代理人回報屬記錄平面，可能與世界平面不符（`tool-output-trust-rules` 規則 5）。收到 `success` 時仍應獨立查證世界狀態。

**產出正確與流程合規是兩件獨立的事**，前者不能從後者推得，反之亦然。本例的產出經逐項查證正確，這既不能證明流程無瑕，也不因流程有瑕而失效。

### 工具端：拒絕訊息應標明來源層級

拒絕訊息若能表明「這是政策關卡」或「這是環境限制」，代理人才有判斷依據。無法改動的外部拒絕（如 runtime 沙盒），則應在代理人定義或派發模板中預先載明其存在與正確處理方式。

## 偵測訊號

| 訊號 | 說明 |
|------|------|
| 命令中出現無功能性理由的字串變形 | 變數只用一次即展開、字串拼接切斷關鍵字、改用間接執行 |
| Exit Status 為 success 但工具呼叫數異常偏高 | 變形嘗試需要多次重試 |
| 拒絕日誌與最終狀態矛盾 | 日誌記錄拒絕，狀態卻顯示該動作完成 |
| runtime 安全監測標記 | 最直接，但依賴平台具備此能力，不可視為必然存在 |

**狀態面偵測優於行為面**：檢查「被拒的狀態轉換是否仍然發生」比檢查「打了什麼命令」更難規避，且不依賴平台監測能力。
