### 實作形態

建立獨立函式 invokeMethodSafely<T>(channel, method, {required tag, arguments})
（非 mixin / base class），放在 lib/platform/method_channel_safety.dart。選擇
函式而非繼承類的理由：兩個呼叫端（CursorLocator、InputBindingChannel）分屬
不同目錄且無其他共享狀態或行為，用 mixin/base class 會強迫兩者共享一個型別
階層，但實際只需共享「一段呼叫邏輯」，函式組合已足夠且耦合最小。

### catch 涵蓋範圍決定（既有實作參考座標第 3 點的判斷）

共用包裝只捕捉 PlatformException 與 MissingPluginException——這兩者是
invokeMethod 本身會拋出的例外，為兩側呼叫端共同需要。cursor_locator.dart
原本多出的 UnsupportedError 分支，捕捉的是呼叫 invokeMethod 之前色彩換算
（Color.toARGB32()，NaN/Infinite 分量觸發）拋出的例外，經
test/platform/cursor_locator_test.dart 的「色彩轉換期例外」測試證實：換算
失敗時 invokeMethod 從未被呼叫（calls 為空）。這屬於 play() 呼叫端自身的
業務邏輯（色彩單位換算），不是「呼叫 method channel」這件事本身，因此不收進
共用包裝，維持在 play() 呼叫端保留獨立的 try { ... } on UnsupportedError。
若收進共用包裝，會讓一個與 method channel 無關的例外型別成為所有呼叫端的
隱性契約，且 input_binding_channel.dart 從未有這類換算邏輯，收進去等於擴大
共用包裝的職責邊界卻無實質共用需求。

### 四條判準逐項對照

- 重複消除：cursor_locator.dart 與 input_binding_channel.dart 的

### 要解決的問題

本專案有三個 method channel 橋接檔，它們在「呼叫原生端並處理失敗」這件事上的處理方式不一致，且其中兩者是同一段邏輯的兩份實作：

| 檔案 | 失敗處理骨架 | 日誌機制 |
|------|------------|---------|
| `lib/platform/cursor_locator.dart` | try / catch PlatformException / catch MissingPluginException / catch UnsupportedError / 記錄後吞掉 | `developer.log` + `_tag`（符合 observability-rules 規則 2） |
| `lib/input/input_binding_channel.dart` | 同一骨架（`_invoke`，前三個 catch 相同） | `debugPrint`（**違反** observability-rules 規則 2），且 `[input-binding]` 前綴字面重複寫在 7 處呼叫點 |
| `lib/platform/fullscreen_detector.dart` | 監聽方向為主，無 invoke 骨架 | `debugPrint`（**違反**同一規則） |

兩個問題疊在一起：邏輯重複，以及既有的日誌規則違規。Phase 4 的 coupling 視角指出，處理前者的動作會自然涵蓋後者——抽取共用實作時必然要決定用哪個日誌機制，而合規的選擇只有一個。
