### 問題根因
MainFlutterWindow.swift:745-747（修正前）以 `as? Int` 轉型 play 呼叫的兩個
參數，轉型失敗時值變 nil，但緊接的 NSLog 僅印出 nil，且不論轉型是否成功
一律 `result(nil)`（回報成功）。log 因此無法區分「Dart 端根本沒帶這個
參數」與「帶了但型別不符」，且 Dart 端完全收不到任何失敗訊號——
即便 1.4.0-W2-007 已在 Dart 側建好 `invokeMethodSafely` 的
PlatformException/MissingPluginException catch-log 包裝，Swift 端從未
回傳過會觸發該包裝的錯誤，故該包裝對這個失效模式從未生效過。

### 影響範圍
- macos/Runner/MainFlutterWindow.swift（CursorLocatorBridge.handle）
- 間接關聯 lib/platform/cursor_locator.dart 與
  lib/platform/method_channel_safety.dart（Dart 端既有 catch-log 路徑，
  本票不改動，但其能否感知失敗取決於 Swift 端是否回傳 FlutterError）

### 相關 Error Pattern
未查得直接對應的既有 error-pattern；本票屬 1.4.0-W2-007 明文延後的
決策點（見 method_channel_safety.dart 檔頭註解：「是否改為讓呼叫端能
感知失敗，屬 1.4.0-W2-016 評估範圍」）。

### 修改內容
`macos/Runner/MainFlutterWindow.swift` CursorLocatorBridge：

1. 新增 `CursorLocatorArgument<T>`（success/missing/typeMismatch 三態）與
   `extractCursorLocatorArgument`，取代原本單純 `as? Int` 靜默變 nil。
   `.missing` 對應「Dart 端沒帶這個鍵」，`.typeMismatch` 對應「帶了但型別
   不符」，兩者呼叫端各自可辨識並記錄。
2. `handle` 的 play 分支拆出 `handlePlay`：兩個參數皆成功才視為合法呼叫、
   照舊 NSLog 記錄成功事實並 `result(nil)`；任一失敗則對每個鍵各自呼叫
   `logArgumentFailure`（帶 key + 原始 `call.arguments` 內容），並以
   `FlutterError(code: "invalid_arguments", ...)` 回覆，取代原本一律
   `result(nil)`。
3. 移除 :750 log 字面內嵌的「（骨架階段僅記錄，不播放特效）」，改把階段
   說明留在 class 上方的 doc comment（開發脈絡，非長壽 runtime log）。

### 驗收項 2：FlutterError 評估與記錄
改為 `result(FlutterError(...))` 而非維持 `result(nil)`。影響評估：

- Dart 端 `cursor_locator.dart` 的 `play()` 透過
  `method_channel_safety.dart` 的 `invokeMethodSafely` 呼叫 channel；該
  函式已捕捉 `PlatformException` 並以 `developer.log(level: 900)` 記錄後
  回傳 null（1.4.0-W2-007 建置，但此前 Swift 端從未回傳過
  PlatformException，故此路徑對本失效模式從未生效）。Swift 端
  `FlutterError` 在 Dart 端即對應 `PlatformException`（code/message/details
  逐項映射），故本次修改後該 catch-log 包裝會首次針對「參數缺失/型別
  不符」實際生效，Dart 端從此能在 log 看到失敗訊號，且沿用既有「記錄後
  吞掉不外洩」契約，呼叫端行為不變（`play()` 仍不拋例外、仍是
  fire-and-forget）。
- 目前唯一呼叫端 `cursor_locator.dart:44-52` 一律送出型別正確的 int
  （`duration.inMilliseconds` / `Color.toARGB32()`），正常呼叫路徑不受
  影響；`test/platform/cursor_locator_test.dart` 三個既有例外測試（mock
  handler 直接丟例外或未註冊）維持通過，因為它們測的是 mock 層直接拋出
  的例外，不經過本次修改的 Swift 端邏輯。
- 結論：採用 FlutterError 回覆，不再維持 `result(nil)` 靜默成功。

### Phase 4：多視角審查（自行執行，等價 /parallel-evaluation）
- 正確性：channel 名/方法名/參數鍵字面完全未改動，
  `test/platform/channel_contract_test.dart` 7 項字面守衛測試通過；成功
  路徑（Dart 端一律送型別正確參數）行為不變，僅失敗路徑從靜默成功改為
  可觀測。
- 複雜度/耦合：新增一個 2-case 泛型 enum + 一個泛型提取函式 + 一個
  handler 方法，均為滿足「區分未帶參數/型別不符」此驗收項的必要最小結構；
  曾考慮把兩次 `logArgumentFailure` 呼叫收斂成迴圈（`[(key, outcome)]`
  陣列），評估後認為 2 個項目引入 tuple 陣列反而增加閱讀負擔，維持現狀
  兩次顯式呼叫。
- 精簡（消除特殊情況）：`handlePlay` 用 guard 一次判斷兩個鍵皆成功，
  失敗路徑扁平化（不巢狀 if/else），符合「消除特殊情況」的簡潔風格。
- 可觀測性：失敗 log 同時含操作名稱、元件標籤 `[cursor-locator]`、觸發
  鍵名、原始 arguments 內容，符合
  `.claude/rules/core/observability-rules.md` 規則 5 對平台互動 log 的
  最低要求。
- 結論：無需進一步重構，程式碼品質 A。
