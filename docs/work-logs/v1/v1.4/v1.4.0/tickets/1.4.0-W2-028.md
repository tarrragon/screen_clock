## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

**index.lock 競爭者不是單一固定進程，而是一類會被反覆觸發的機制：任何併發執行的 git 唯讀子命令（`git status`、`git diff-tree`、`git log`）在 refresh index 時會短暫寫入 `.git/index.lock`，與同時發生的 `git add`/`git commit` 產生真實碰撞。** 本專案的 hook 系統在每次 Bash 呼叫的 PostToolUse 階段會連續呼叫多個這類唯讀 git 子命令，且存在四個 hook 對「git commit 後」邏輯重複註冊（見下），使碰撞機率提高；此外背景派發代理人與 PM 共用同一 cwd（未使用 worktree 隔離）時，兩邊各自的 git 子行程亦可能同時存在。

### 影響範圍（已驗證 vs 未驗證）

**已驗證的事實**：

1. `.claude/settings.json` 的 PostToolUse Bash matcher 同時註冊四個獨立 hook，皆對「git commit」重複實作相同邏輯：
   - `post-git-commit-hook.py`（自稱「合併版」，docstring 明載合併自下列 3 個 hook，但另外 3 個仍獨立存在於 settings.json，並未移除）
   - `commit-handoff-hook.py`（同一套 handoff 提醒邏輯）
   - `changelog-update-hook.py`（同一套 CHANGELOG 檢查邏輯，內部呼叫 `git diff-tree --no-commit-id --name-only -r HEAD` 與 `git log -1 --format=%s`）
   - `post-commit-fetch-hook.py`（同一套背景 fetch 邏輯，呼叫 `git fetch --quiet --all`）
   實測：本 session 於 17:42:53-17:42:54 同一次 `git commit`（commit `0b2ade4`）觸發 `post-git-commit-hook`、`commit-handoff`、`changelog-update-hook` 三份獨立日誌記錄同一事件，證實四個 hook 確實同時對同一 git commit 命令各自執行一遍，而非「合併版」取代舊三者。

2. `.git/index.lock` 的競爭者身分包含「git 唯讀子命令本身」，非僅限寫入命令。**重現實驗**（見下節）證實：併發執行 `git status --porcelain` / `git diff-tree` / `git log -1` 的迴圈，與另一行程的 30 次 `git add` 呼叫並行時，第 8 次 `git add` 出現 `fatal: Unable to create index.lock: File exists`。這推翻了 ticket why 欄與 `bash-tool-usage-rules.md` 規則三「git status 屬唯讀不觸發 Hook / 不佔用 lock」的假設——git 內部在 refresh index cache（更新 stat 時間戳）時會短暫建立並釋放 `index.lock`，此行為與命令是否「語意唯讀」無關。

3. `.claude/dispatch-active.json` 於分析當下（17:42:18 起）記錄本次 thyme 派發為活躍背景代理人，同時段 PM 在同一 cwd（無 worktree 隔離，`1.4.0-W2-006` ticket 明載「不使用 isolation:worktree」）持續執行多次 `git commit`（`0b2ade4` 17:33、`794c106` 17:24、`da0df99`/`2fa93d3`/`6c8c352` 等 append-log commit）。此為 PM 與背景代理人共用 cwd 情境的即時活體案例，與 `worktree-auto-commit-hook.py` docstring 記載的 W1-059 race（PM + 背景代理人共用 cwd 導致 `git add -A` 搶先代捕）屬同一機制家族，差異僅在該 hook 僅於 worktree 環境觸發、本案為主 repo 模式故該特定 hook 未介入，但「PM 與背景代理人的 git 子行程可能同時存在於同一 repo」此一結構性條件確認成立。

**仍未驗證的假設**：

- 尚未能在 1.4.0-W2-006 收尾當下的確切時間點取得逐秒級 hook 執行日誌以直接證明「就是哪一個具體 hook 呼叫」造成該次串接三連敗；本節重現實驗證明的是「機制存在且可重現」，非「鎖定當次事故的唯一元兇」。
- 未驗證 `git fetch` 是否也會建立 `index.lock`（一般認知 fetch 只操作 refs/objects，不動 index；本次重現實驗未特別隔離測試 fetch，故對 post-commit-fetch-hook.py / post-git-commit-hook.py 內建的 `git fetch --quiet --all` 是否為競爭來源之一，仍未證實，僅能確認其為重複執行造成的額外 git 子行程負載）。
- 未驗證 Claude Code runtime 對同一事件註冊的多個 hook 是否嚴格序列執行或存在併發排程；四個 commit 相關 hook 的日誌時間戳皆落在同一秒或相鄰秒，無法排除序列快速執行的可能性，故「hook 間彼此併發」未達已驗證等級，僅「PM 主線程 git 行程與背景代理人 git 行程併發」與「唯讀 git 子命令會短暫佔用 index.lock」兩點達已驗證等級。
