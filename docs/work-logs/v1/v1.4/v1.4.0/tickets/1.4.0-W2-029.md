| post-commit-fetch-hook.py | commit 成功後背景 git fetch --quiet --all，逾時 4s 印 WARNING | `run_background_fetch()`（子邏輯 3，L259-283） | 完整涵蓋 |

附帶發現（非缺口，屬合併順帶修正）：
- changelog-update-hook.py 原始碼讀取 `input_data.get("tool_result", {})`，但 PostToolUse payload 實際欄位為 `tool_response`；該 hook 因欄位名錯誤，實際上從未能正確判斷 commit 是否成功（隱性失效）。合併版統一改用 `tool_response`，等於在合併過程中修正此既有 bug，非行為遺失。
- post-commit-fetch-hook.py 原始碼讀取頂層 `data.get("stdout", "")`（不存在於 payload，恆為空字串），配合判斷式 `"create mode" not in stdout and "] " not in stdout: return`，兩條件在空字串下恆為真，等同該 hook 原本恆為 no-op（fetch 從未真正執行）。合併版改用 `tool_response.stdout` 並統一 `is_commit_successful()`，修正此 bug，fetch 現在能正確觸發。
- commit-handoff-hook.py 原始碼正確使用 `tool_response`，行為與合併版逐項一致，無差異。

結論：無功能缺口，可安全移除三個被合併 hook 的 settings.json 註冊（保留檔案本身）。

#### 附帶發現的處置：已升級為 error-pattern

執行者於 acceptance 1 逐項比對時發現，`changelog-update-hook.py` 與 `post-commit-fetch-hook.py` 讀取的 payload 欄位有誤。PM 查證確認：

| 檔案 | 讀取方式 | 判定 |
|------|---------|------|
| `post-git-commit-hook.py:120` | `input_data.get("tool_response") or {}` | 正確（PostToolUse payload 的工具結果確在 `tool_response`） |
| `changelog-update-hook.py:126` | `input_data.get("tool_result", {})` | 欄位名錯誤，恆為空 dict |
| `post-commit-fetch-hook.py:37` | `data.get("stdout", "")` | 欄位層級錯誤（頂層而非巢狀），恆為空字串 |

兩者取得空值後，其 commit 成功判斷因 stdout 不含成功特徵而回傳 False 並 return，故**自註冊起未曾實際執行**。CHANGELOG 檢查與背景 fetch 兩項功能長期為靜默 no-op，且因無例外、無錯誤日誌、退出碼正常，未被任何檢查機制捕獲。

此現象亦精確解釋了觸發本次調查的原始觀察——每次 commit 出現兩份一字不差的 handoff 提醒，而 CHANGELOG 提醒並未重複：同批重複註冊的三者中，只有 `commit-handoff-hook.py` 欄位讀取正確因而是活的。**能被看見的是重複，不是缺席。**

依 quality-baseline 規則 6，本現象屬跨專案可重現的結構性錯誤（替換專案名與檔案路徑後，「事件處理器讀錯 payload 欄位 → 帶預設值的取值吸收錯誤 → 走無事可做分支 → 靜默失效」的鏈條仍成立），已直接記錄為 `PC-SCLK-007`（含實作端、驗證端、審查端三層防護與四項偵測訊號），並同步 error-patterns README 索引。

**發現路徑值得記錄**：本缺陷非被任何機制捕獲，而是因派發時設下「比對先於移除、不涵蓋即停手、不得逕自補寫合併版」的前置條件，執行者必須閱讀原始碼逐項比對才撞見。若當時逕行移除註冊，這兩個 hook 會被當作「功能已由合併版接手」而移除，缺陷連同其存在一併消失。此點已寫入 PC-SCLK-007 的實例節。
