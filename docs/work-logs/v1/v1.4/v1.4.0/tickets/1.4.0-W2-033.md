### 派發前現況查證（PM，2026-08-01）

建票時的假設是「把 Swift 測試加進既有測試流程」。實際查證後，**既有測試流程並不存在**——本票範圍因此比原設想更基礎。接手者應獨立重新驗證（PC-162）。

| 檢查項 | 現況 | 查證方式 |
|--------|------|---------|
| CI 設定 | 不存在 | `ls .github/workflows/` 目錄不存在 |
| 測試執行腳本 | 無 | `scripts/` 僅 `build-release.sh`、`sign-and-notarize.sh`；`grep -rln "flutter test" scripts/` 零命中 |
| CLAUDE.md 測試指令 | 無記錄 | `grep -n "flutter test\|xcodebuild" CLAUDE.md` 零命中 |
| `flutter test` 的文件足跡 | 僅歷史 worklog | `grep -rln "flutter test" docs/` 命中皆為 v1.0.x 的 ticket 與 worklog |

即 Dart 側測試的執行方式目前也只存在於各代理人的既有知識與歷史紀錄中，未被任何工具或文件固定。

### 對 acceptance 2 的影響

acceptance 2 要求「Swift 測試納入常規測試執行路徑，非僅手動一次性執行」。既然常規路徑不存在，本票須先決定該路徑的形態。三個候選：

| 方案 | 內容 | 取捨 |
|------|------|------|
| A 統一測試腳本 | `scripts/` 下新增單一入口，同時跑 `flutter test` 與 `xcodebuild test` | 最小可行；不依賴外部服務；但仍需人或 agent 主動執行 |
| B CI | 建立 GitHub Actions workflow，push/PR 觸發 | 真正的「不需記得執行」；但需 macOS runner（成本較高），且本專案至今無 CI 屬更大的引入決策 |
| C 僅文件記錄 | 於 CLAUDE.md 記錄兩條命令 | 成本最低，但依 `.claude/rules/core/opinionated-default-design.md`，「寫文件提醒遵守」正是工具預設行為不足的信號，不應作為終局方案 |

**PM 傾向 A 為本票範圍，B 另行評估建票**。理由：A 使兩套測試有單一入口（消除「忘記還有 Swift 測試」的可能），且是 B 的前置——CI 最終也會呼叫同一個腳本。C 不可單獨採用，但腳本仍需在 CLAUDE.md 留指引，故 A 實際包含 C。

此處僅為傾向，非強制。若執行者評估後認為應直接做 B，須說明理由並評估 macOS runner 的實際約束。

### 與 W2-006.1 的銜接

`1.4.0-W2-006.1` 已建立可執行的 XCTest 路徑，其 Test Results 記錄了實測通過的完整命令：

```
xcodebuild test -workspace macos/Runner.xcworkspace -scheme Runner -configuration Debug \
  -destination 'platform=macOS' -only-testing:RunnerTests/CursorScreenLocatorTests
```

該票並記錄兩項與本票直接相關的約束：模組名以 `PRODUCT_NAME=screen_clock` 為準（非 target 名 `Runner`）；`@testable import` 僅 Debug configuration 可用。腳本設計須保留這兩點。

### acceptance 3 的權限彈窗風險現況

`W2-006.1` 的測試為純函式群組，未觸發權限彈窗（其 Test Results 記錄 B-6/B-7 為 N/A）。真正的風險在 `1.4.0-W2-006.2` 的 app-hosted 測試群組 F——宿主 app 啟動時 `MainFlutterWindow` 的 CGEventTap 可能彈出輔助使用權限對話框，阻塞無人值守執行。本票評估此風險時，`.2` 尚未執行，故只能就機制面評估與預留因應，不能宣稱已實測排除。
