### 派發前現況查證（PM，2026-08-01）

建票時的假設是「把 Swift 測試加進既有測試流程」。實際查證後，**既有測試流程並不存在**——本票範圍因此比原設想更基礎。接手者應獨立重新驗證（PC-162）。

| 檢查項 | 現況 | 查證方式 |
|--------|------|---------|
| CI 設定 | 不存在 | `ls .github/workflows/` 目錄不存在 |
| 測試執行腳本 | 無 | `scripts/` 僅 `build-release.sh`、`sign-and-notarize.sh`；`grep -rln "flutter test" scripts/` 零命中 |
| CLAUDE.md 測試指令 | 無記錄 | `grep -n "flutter test\|xcodebuild" CLAUDE.md` 零命中 |
| `flutter test` 的文件足跡 | 僅歷史 worklog | `grep -rln "flutter test" docs/` 命中皆為 v1.0.x 的 ticket 與 worklog |

即 Dart 側測試的執行方式目前也只存在於各代理人的既有知識與歷史紀錄中，未被任何工具或文件固定。

### 對 acceptance 2 的影響

acceptance 2 要求「Swift 測試納入常規測試執行路徑，非僅手動一次性執行」。既然常規路徑不存在，本票須先決定該路徑的形態。三個候選：

| 方案 | 內容 | 取捨 |
|------|------|------|
| A 統一測試腳本 | `scripts/` 下新增單一入口，同時跑 `flutter test` 與 `xcodebuild test` | 最小可行；不依賴外部服務；但仍需人或 agent 主動執行 |
| B CI | 建立 GitHub Actions workflow，push/PR 觸發 | 真正的「不需記得執行」；但需 macOS runner（成本較高），且本專案至今無 CI 屬更大的引入決策 |
| C 僅文件記錄 | 於 CLAUDE.md 記錄兩條命令 | 成本最低，但依 `.claude/rules/core/opinionated-default-design.md`，「寫文件提醒遵守」正是工具預設行為不足的信號，不應作為終局方案 |

**PM 傾向 A 為本票範圍，B 另行評估建票**。理由：A 使兩套測試有單一入口（消除「忘記還有 Swift 測試」的可能），且是 B 的前置——CI 最終也會呼叫同一個腳本。C 不可單獨採用，但腳本仍需在 CLAUDE.md 留指引，故 A 實際包含 C。

此處僅為傾向，非強制。若執行者評估後認為應直接做 B，須說明理由並評估 macOS runner 的實際約束。

### 與 W2-006.1 的銜接

### acceptance 3 的權限彈窗風險現況

`W2-006.1` 的測試為純函式群組，未觸發權限彈窗（其 Test Results 記錄 B-6/B-7 為 N/A）。真正的風險在 `1.4.0-W2-006.2` 的 app-hosted 測試群組 F——宿主 app 啟動時 `MainFlutterWindow` 的 CGEventTap 可能彈出輔助使用權限對話框，阻塞無人值守執行。本票評估此風險時，`.2` 尚未執行，故只能就機制面評估與預留因應，不能宣稱已實測排除。

方案採用：A（統一測試腳本），未改為 B（CI）。

理由：本專案至今無 `.github/workflows/`，導入 CI 是獨立於本票範圍的決策（需評估
GitHub Actions macOS runner 成本——macOS runner 分鐘數計費倍率為 Linux 的 10 倍，
且本機測試 xcodebuild 段單次即需約 6-24 秒建置 + 測試時間，長期跑在 CI 上的成本
需另行估算；亦需確認 remote 是否為 GitHub 及是否已有 Actions 額度）。A 是 B 的
前置：CI workflow 最終仍會呼叫同一支腳本，先把「單一入口」做對，之後接 CI 只是
在 workflow yaml 內呼叫 `scripts/run-tests.sh`，不需重新設計退出碼合併邏輯。
**建議另建 DOC/ANA ticket 評估 CI 導入**（範圍：runner 選擇與成本、觸發策略
push/PR、是否需要 secrets），本票不涵蓋。

實作內容：

新增 `scripts/run-tests.sh`（可執行權限 755，風格對齊既有 `scripts/build-release.sh`）：
1. 依序執行 `flutter test` 與 `xcodebuild test`，兩段皆完整跑完不因前段失敗而跳過
   （不用 `set -e`，改為個別擷取 `$?` 後續判斷），確保任一段失敗都能看到另一段的
   完整結果，而非在第一個失敗處中止。
2. `xcodebuild test` 呼叫確認**不需要** `-only-testing:RunnerTests`：Runner scheme
   的 xcscheme 檔（`macos/Runner.xcodeproj/xcshareddata/xcschemes/Runner.xcscheme`）
   TestAction 已將 RunnerTests target 設為 `skipped = "NO"`，預設即涵蓋，額外加
   `-only-testing` 反而是多餘限制。已實測確認（見 Test Results）。
3. 兩段退出碼各自保存為 `DART_EXIT` / `SWIFT_EXIT`，任一非 0 即整體失敗；兩者皆
   非 0 時回傳 `DART_EXIT`（Dart 側優先，因其執行順序在前，符合腳本標頭文件化的
   退出碼約定）。錯誤訊息一律寫入 stderr（`.claude/rules/core/observability-rules.md`
   規則要求）。
4. 已知風險段落（acceptance 3）：說明現況 RunnerTests 僅含純函式測試不觸發權限
   彈窗（本票已實測確認），並記錄若日後 `1.4.0-W2-006.2` 加入 app-hosted 測試群組
   時的因應方向（`-skip-testing` 排除或另立 test plan），但明確標註此為機制面預留
   而非已實測排除——因 `.2` 尚未執行，屆時該測試群組尚不存在。

修改 `CLAUDE.md`：Section 7「專案文件」新增「測試執行」小節，記錄
`scripts/run-tests.sh` 為單一入口，並列出底層兩條指令（含模組名
`PRODUCT_NAME=screen_clock`、`@testable import` 僅 Debug 可用兩項約束，繼承自
`1.4.0-W2-006.1`）。依 `.claude/rules/core/opinionated-default-design.md`：純文件
提醒是工具預設行為不足的信號，故實際落點是腳本本身（工具預設行為），CLAUDE.md
僅記錄「腳本是入口」，不取代腳本。

過程中發現並修正一項可攜性問題（非 acceptance 範圍但屬品質基線規則 3「設計問題
立即修正」）：初版腳本錯誤訊息字串為 `"...失敗（exit $DART_EXIT）"`（`$VAR` 緊鄰
全形符號、無大括號），實測發現此寫法在本機 `/bin/bash`（macOS 內建 3.2.57，Apple
因 GPLv3 授權考量未隨系統升級）搭配 `set -u` 時會誤判為 unbound variable 並以
exit 127 crash——這只在測試失敗分支才會觸發，測試皆通過時不會發現。已改用
`${DART_EXIT}` / `${SWIFT_EXIT}` 大括號寫法修正，並以 mock 替身（假造
flutter/xcodebuild 呼叫回傳指定退出碼）於 scratchpad 驗證四種組合（皆通過/僅
Dart 失敗/僅 Swift 失敗/皆失敗）的退出碼合併與錯誤訊息輸出皆正確，驗證後清除
scratchpad 暫存檔，未留存於專案內。
