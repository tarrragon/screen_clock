### 實驗方法

### 關鍵更正：`changelog-update-hook` 不是死的

執行者原判定其為死（「所有日誌僅含 Hook execution time」）。PM 複驗推翻此判定——1542 個日誌檔中確有 18 行實際輸出，時間橫跨 2026-07-31 08:17 至 2026-08-06 15:31（後者為本 session 的 commit）。執行者的取樣未涵蓋到這批稀疏樣本（18/1542 比例極低）。

根因在 `is_commit_successful()`（`.claude/hooks/changelog-update-hook.py:64-74`）：

```python
def is_commit_successful(tool_result: dict) -> bool:
    stdout = tool_result.get("stdout", "")   # tool_result 恆為 {} → ""
    stderr = tool_result.get("stderr", "")
    if "nothing to commit" in stdout or "Aborting" in stdout:
        return False
    if "nothing to commit" in stderr or "Aborting" in stderr:
        return False
    return True                               # 空字串無失敗特徵，恆走此路
```

欄位確實讀錯（`tool_result` 應為 `tool_response`），但判定函式的形態是**「找不到失敗特徵就算成功」**。空字串當然找不到，於是恆回傳 `True`，流程繼續往下，最終真的印出提醒。

**實際後果不是「不執行」，是「失去判別能力」**——它對每一次 `git commit` 命令都當成功處理，包括失敗的、被 hook 擋下的、`nothing to commit` 的。這比靜默失效更值得修：靜默失效是少做事，這是做錯事。

### 「兩份一字不差的提醒」來源

實證時間點 2026-07-31 17:24:44，兩份輸出分別來自：

- `post-git-commit-hook` 的 handoff 子邏輯：`handoff: 輸出提醒（type=docs）`
- `commit-handoff-hook`（獨立版）：`偵測到 git commit 成功（type=docs），自動跳過場景 #16，輸出 Skip16 提醒`

兩者在同一秒對同一次 commit 各自觸發。`post-commit-fetch-hook` 未貢獻任何輸出。

### 已驗證事實 vs 仍未驗證的假設

**已驗證**：四者的日誌實況與 payload 讀取欄位；`changelog-update-hook` 有實際輸出且其判定函式恆回傳 True；重複提醒的兩個來源。

**未驗證**：`changelog-update-hook` 的 18 行輸出中，有多少對應的 commit 實際失敗（即誤報率）。本次僅證實「判別能力喪失」，未量化其誤報比例。
