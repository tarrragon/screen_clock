## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->

### 問題根因

`SettingsModel.fromJson()` 從不讀取 `schemaVersion`，版本相容完全建立在「欄位缺失 → 取 `defaults()` 值」這單一機制上。`schemaVersion` 只在 `toJson()` 寫出，是單向的審計標記而非解析分支依據。

直接後果：解析器沒有任何「這筆資料是哪一版寫的」的認知，因此無法對「同名欄位語意改變」做版本分支。相容性的成立前提被完全外部化為人為紀律（SPEC-009 INV-03「只加欄、不改型別、不刪欄」），而該紀律無任何機械強制訊號。

放大因素（本票實驗新發現，SPEC-009 未記載）：`_asDouble` / `_asInt` / `_asBool` 等容錯轉換函式是**寬鬆轉型**而非嚴格型別檢查。`_asInt(2.9)` 回傳 `2`、`_asDouble('3.5')` 回傳 `3.5`、`_asBool('true')` 回傳 `true`。這使得型別變更不但不會報錯，還會「看似成功」地產生被截斷或被重新詮釋的值。容錯設計在此處反向放大了 INV-03 違規的隱蔽性。

**修正 1.4.0-W1-007 的既有描述**：「相容性靠欄位缺失取預設值」有一處例外。`settings_model.dart:70-71` 的 `bindingsSeeded` fallback 是**字面 `false`**，不是 `d.bindingsSeeded`（`defaults()` 為 `true`）：

```dart
bindingsSeeded:
    _asBool(json[AppSettingsKeys.bindingsSeededKey]) ?? false,
```

這是刻意設計——若 fallback 取 `defaults()` 的 `true`，舊資料會被誤判為已遷移，`_migrateBindingSeed()` 永不觸發。因此 `bindingsSeeded` 並非一般設定欄位，而是**偽裝成欄位的版本標記**：它承擔了 `schemaVersion` 本該承擔的「這筆資料是舊格式」的判別職責。這正是「版本號不參與解析」所造成的架構代償。

### 實驗發現

**已驗證的事實**：

1. **`schemaVersion` 對解析零影響**（E1）。缺失、`99`、`'garbage'`、`-1` 四種輸入產生**完全相等**的 `SettingsModel`。版本號可以是任意值甚至不存在，行為不變。

2. **情境一（欄位型別變更）——不拋例外，分兩種後果**（E2）：
   - 可轉型時**靜默寬鬆轉型**：`targetScreenIndex: 2.9 → 2`（無條件截斷）、`'3.5' → 3.5`、`'true' → true`。這是最危險的一類——資料看似成功載入，實則已被靜默改值。若把 `double` 欄改為 `int`，全體舊使用者的小數設定會被截斷且無任何訊號。
   - 不可轉型時**靜默取預設**：Map 給 double 欄、int 給 String 欄、非法字串給 Color 欄，一律 fallback 到 `defaults()`。使用者設定被靜默重置，且**無日誌**。
   - 巢狀結構同理：`bindings` 非清單 → 空清單（E2c）。

3. **情境二（同名欄位語意變更）——現行機制完全無法偵測**（E3）。型別不變、語意改變時，舊值被新語意原樣接收，零例外零警示。`birthDate` 若由「epoch 毫秒」改為「epoch 秒」，同一時刻的舊值 `946684800000` 會被解讀為 2000 年，而秒制的 `946684800` 被當毫秒解讀成 **1970-01-12**。資料被誤讀而非崩潰——這是三情境中最惡劣的一種，因為錯誤會被靜默持久化（下次 `save()` 就寫回錯誤值，原始資料永久遺失）。

4. **情境三（欄位移除）——雙向皆有損，方向 B 更嚴重**（E4）：
   - 方向 A（新版讀舊資料）：舊資料中已移除的多餘欄位被靜默忽略，不影響解析。這個方向是**安全的**。v1 資料讀入後 `lifeTimerMode=false`、`bindings=[]`、`bindingsSeeded=false`，隨後由 `_migrateBindingSeed()` 補入預設綁定。
   - 方向 B（舊版讀新資料）：舊版程式碼只認得自己那代的 key，`[schemaVersion, lifeTimerMode, bindings, bindingsSeeded]` 全部靜默丟棄；一旦舊版執行 `save()`，`toJson()` 只寫出自己認得的欄位，**新版資料被永久截斷**。降版（使用者回退舊版 app）等同資料遺失。現行機制對此零防護。

5. **`bindingsSeeded` 使 v3 存在兩種資料形態**（E5）。同為 `schemaVersion: 3`，`bindingsSeeded` 可為 `false`（10284df 之前寫出）或 `true`（之後寫出），migration 觸發依旗標值而非版本號。版本號在此已喪失識別資料形態的能力。

6. **降級永不崩潰，但降級結果不等於 `defaults()`**（E6）。外來 JSON `{"foo":1,"bar":[1,2,3]}` 解析成功不拋例外（INV-08 成立），但結果 `!= defaults()`——`bindings` 為空、`bindingsSeeded` 為 `false`，而 `defaults()` 是 1 筆綁定 + `true`。需經 `_migrateBindingSeed()` 才收斂。此差異 SPEC-009 A.6 恢復模型未記載。

**仍未驗證的假設**：使用者裝置上各版本存檔的實際分佈；降版（方向 B）在實務上的發生率（macOS app 降版需使用者主動替換 bundle，機率低但非零）。

**與 SPEC-009 INV-03 的比對結論**：INV-03（只加欄、不改型別、不刪欄）確實是相容性成立的**充分條件**——只要遵守，三情境無一會發生。但實驗顯示違反 INV-03 的**代價是靜默資料損壞而非崩潰**，且無任何自動化訊號。SPEC-009 稱其為「本契約最脆弱的一條」屬實，且實驗補充了 SPEC-009 未預見的一點：容錯轉換函式的寬鬆轉型特性讓違規更難察覺（不是「取預設」而是「取到一個看似合理的錯值」）。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->

### 分析結論

現行「加欄 + 預設值 fallback」策略在 INV-03 被遵守的前提下**功能上是成立且足夠的**；問題不在解析能力，而在**違規偵測能力為零**。因此解法方向應是補上偵測訊號，而非重建解析機制。

一項架構觀察：`bindingsSeeded` 的存在本身就是「版本號不參與解析」的代償產物——當需要區分資料形態時，開發者被迫再造一個欄位級版本標記。若不處理，未來每次需要 migration 都會再長出一個 `xxxSeeded` 旗標，旗標間的組合狀態將指數成長。這是本票認為必須明文治理的真正理由。

### 方案比較表

| 維度 | A 維持現狀 + 契約文字約束 | B 導入版本分支解析 | C 維持加欄策略 + golden fixture 機械訊號 + 明文升級觸發條件（**建議**） |
|------|------------------------|-------------------|--------------------------------------------|
| 做法 | 不改 code，靠 SPEC-009 INV-03 與 code review 把關 | `fromJson` 讀 `schemaVersion`，依版本走不同解析路徑 / migration 函式鏈 | 保留現行解析；補上逐版 golden fixture 迴歸測試；契約明文「何時必須升級為 B」 |
| INV-03 違規偵測 | 無（人工 review，已證實不可靠） | 不需要（可版本分支處理語意變更） | 有：改型別 / 刪欄立即測試轉紅 |
| 對 `1.4.0-W1-001` 影響 | 無 | 大：需先重構 `fromJson`，W1-001 被阻塞 | 無：W1-001 可照原計畫執行 |
| 對既有使用者資料風險 | 維持現狀（風險潛伏） | 中：重構解析路徑本身有回歸風險，四種形態皆需回歸驗證 | 低：不動 production code，僅加測試 |
| 實作範圍 | 0 | `settings_model.dart` 大幅重構 + migration 層 + 四形態回歸測試 | `test/models/settings_model_test.dart` 新增 fixture 矩陣 + SPEC-009 條款 |

**選 C 的理由**：實驗證明痛點是「違規無訊號」（quality-baseline 規則 3 要求的設計問題），而非「無法解析舊資料」。B 是針對「同名欄位語意變更」的解法，但該需求目前不存在，且 SPEC-008 FR-06 的 schema 4 是純加欄。C 以最小改動關閉真正的缺口，並把 B 保留為有明確觸發條件的升級路徑（而非無 trigger 的「以後再說」，符合 decision-trigger-binding 規則）。

**B 的升級觸發條件**（寫入 SPEC-009，由 `1.4.0-W1-016` 承接）：出現下列任一情況時，必須先引入以 `schemaVersion` 分派的顯式 migration 層，才能進行該變更：

| 觸發 | 說明 |
|------|------|
| 需變更既有欄位的型別 | 實驗 E2 證實會靜默截斷或重置 |
| 需變更既有欄位的語意 / 單位 | 實驗 E3 證實會靜默誤讀並持久化 |
| 需移除既有欄位 | 實驗 E4 證實方向 B 造成截斷 |
| migration 旗標累積達 3 個 | 旗標組合狀態複雜度超過版本號分派的成本 |

**給 W1-001 的三點執行提醒**（不改變其 acceptance，屬實作注意事項）：

1. **新欄位的單位必須寫進欄位名或註解**。「特效時長」若以毫秒儲存，命名應顯性（如 `cursorEffectDurationMs`）。實驗 E3b 證明單位語意一旦事後改變，舊資料會被靜默誤讀成完全錯誤的值且無法回溯。這是零成本的預防。

### bindingsSeeded 同版擴充的決議

**決議：維持現狀，不追認為獨立 schema 版本；改以契約明文歸類為「欄位級 migration 旗標」並建立治理規則。**

理由：

1. **追認在行為上是空操作**。實驗 E1 已證實 `fromJson` 完全不讀 `schemaVersion`。將 10284df 追認為 v4 不會改變任何一行解析行為，純屬重新命名。
2. **追認無法回溯已寫出的資料**。10284df 之後寫出的存檔硬編碼 `schemaVersion: 3`，追認後這批資料的版本號與新定義不符，反而**製造**新的形態分歧而非消除既有分歧。
3. **追認會產生連鎖版本號膨脹**。若追認為 4，W1-001 須改升 5，且 SPEC-008 FR-06 明文「將 schemaVersion 由 3 升為 4」須同步修訂，代價全落在文件與 ticket 修訂，收益為零。
4. **`bindingsSeeded` 與 `schemaVersion` 語意正交**。前者回答「這筆資料是否已執行過某次 migration」（一次性、單向、由 INV-07 保護），後者回答「這筆資料由哪版寫出」。強行合併兩個正交概念會使兩者都變模糊。

**代價與配套**：維持現狀意味著「同版本號存在兩種資料形態」成為既定事實，必須明文化否則會被下一位開發者當成 bug 或漏看。配套三項（由 `1.4.0-W1-016` 承接）：

- SPEC-009 A.1 欄位表為 `bindingsSeeded` 標註 migration 旗標類別，說明其與 `schemaVersion` 正交、fallback 為字面 `false` 而非 `defaults()` 值及其原因。
- SPEC-009 A.3 明文治理規則：migration 旗標得加欄不升版，但**必須登錄於 A.1 演進表**（10284df 已登錄，維持）；旗標累積達 3 個時觸發升級為版本分支解析（見上方觸發條件表）。
