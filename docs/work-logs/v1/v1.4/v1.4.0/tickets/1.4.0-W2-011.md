### PM 重新界定範圍（承接 1.4.0-W1-017 落地後的實測）

本票原 why 描述的「六處裸字面」為 1.4.0-W1-017 之前的觀察，已作廢並改寫。以下為 PM 於 main（commit 366ed95 之後）實測的現況。

#### 裸字面實際分布

`lib/models/settings_model.dart` 的 `fromJson`（82 行起），每個純量欄位形如：

```dart
fontSize: _resolveField(
  'fontSize',                    // 參數 1：日誌用欄位名（裸字串）
  json['fontSize'],              // 參數 2：raw（裸鍵）
  _asDouble(json['fontSize']),   // 參數 3：parsed（同一 key 再求值）
  d.fontSize,
),
```

| 位置 | 處數 |
|------|------|
| fromJson 純量欄位 12 個 × 3 | 36 |
| toJson 欄位鍵（200 行起，含 schemaVersion） | 13 |
| 合計約 | 49 |

已用常數者僅 `bindings`（139 行）與 `bindingsSeeded` 的參數 2/3（142-143 行）。

#### 核心風險：日誌欄位名與 JSON 鍵可脫鉤

參數 1 與參數 2/3 必須指涉同一欄位，但簽名不強制兩者同源。`settings_model.dart:140-145` 已是活證據——同一欄位參數 1 用裸字串、參數 2/3 用 `AppSettingsKeys.bindingsSeededKey`。若該常數值日後改動，日誌繼續報 `bindingsSeeded`。

此風險與原本的「鍵打錯字靜默落回預設」不同層級：後者影響資料，前者影響觀測性設施本身——用來發現問題的訊號壞掉時，問題不會有訊號。

1.4.0-W1-017 新增的降級日誌測試抓不到此類錯誤：測試斷言日誌含特定欄位名，而斷言用的字面與被測程式同源，改鍵名時兩邊會一起被改。測試與被測程式共用同一錯誤來源時，綠燈不構成證據。因此 acceptance 條 3 要求新增的測試須驗證「日誌欄位名取自鍵常數」這個結構性質，而非再比對一次字面。

#### 三個不走 _resolveField 的例外

| 位置 | 原因 | 處理 |
|------|------|------|
| `_bindingsFromJson`（139 行呼叫） | 非純量，回傳 List 且有略過條目的獨立日誌路徑 | 鍵已用常數，僅需確認日誌名同源 |
| `_asClampedDuration`（152 行呼叫） | 含 clamp 分支，型別錯誤與越界夾制語意不同 | 鍵仍為裸字面，需收斂；日誌路徑獨立需個別確認 |
| `bindingsSeeded`（140 行） | fallback 為字面 `false` 而非 `d.bindingsSeeded`（defaults() 為 `true`） | 刻意差異，見 1.4.0-W2-013；本票不得改動該語意 |

#### 硬約束

鍵名字串值一律不得變更。golden fixture 測試（`test/models/settings_model_test.dart:249` group，1.4.0-W1-015 產出）以既有鍵名定樁，且該 group 檔頭明載禁止修改既有 fixture。本票只改引用方式，不改鍵名值。
