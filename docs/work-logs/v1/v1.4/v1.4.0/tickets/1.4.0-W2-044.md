### 問題根因

守衛 `version-tracking-consistency-guard-hook.py` 的 `CLOSED_BY_TICKET_ID_PATTERN`（L87-88）僅接受 Ticket ID 格式，未涵蓋框架 issue 引用格式 `owner/repo#N`。20 張以框架 issue 關閉的票每次 session-start 產出假警告。

### 影響範圍

- 檔案：`.claude/hooks/version-tracking-consistency-guard-hook.py`（守衛值域）、`.claude/skills/framework-issue/SKILL.md`（未規範 `closed_by` 填法）
- 影響：每次 session-start 20 行噪音，稀釋守衛訊號價值
- 已驗證事實：20 張票的 closed_by 值皆對應真實框架 issue（抽樣 3/20 驗證通過）

### 相關 Error Pattern

無直接對應的 error pattern。本問題是 tool-output-trust 規則 6 的實例（驗證端未同步建立端演進）。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題定性

本問題屬**框架層**（非專案層）。判定依據：

1. 受影響的守衛 `version-tracking-consistency-guard-hook.py` 位於 `.claude/hooks/`，為框架資產
2. 受影響的規範 `framework-issue/SKILL.md` 位於 `.claude/skills/`，為框架資產
3. 替換專案名稱和檔案路徑後問題仍成立——任何使用此框架的專案，以框架 issue 關閉本地 ticket 時都會遇到相同警告
4. W2-043 已定案：`.claude/` 本地修改會被 sync-pull 覆蓋，修復落點必須在上游

### 建立端歸屬

| 元件 | 角色 | 現況 |
|------|------|------|
| `framework-issue/SKILL.md` 路徑 A | 建立端（定義框架升級關閉流程） | 未規範 `closed_by` 填法（規範缺口） |
| `version-tracking-consistency-guard-hook.py` L87-94 | 驗證端（檢查 `closed_by` 合法性） | 值域僅含 Ticket ID 和 `none`，未涵蓋框架 issue 引用 |

依 tool-output-trust 規則 6：建立端已演進（framework-issue 關閉協議建立），驗證端未同步。以建立端為準，20 張票的 `closed_by` 填法正確，守衛值域需擴展。

### 候選方案

### 方案 A：放寬守衛值域，接受 `owner/repo#N` 格式

**做法**：在 `CLOSED_BY_TICKET_ID_PATTERN` 旁新增 `CLOSED_BY_FRAMEWORK_ISSUE_PATTERN = re.compile(r"^[a-zA-Z0-9_-]+/[a-zA-Z0-9_-]+#\d+$")`，L381 判斷時兩個 pattern 任一命中即合法。

| 利 | 弊 |
|----|-----|
| 最小改動，精確解決問題 | 守衛無法驗證 issue 是否真實存在（但現行守衛也不驗證 ticket ID 是否真實存在，一致性無損） |
| `closed_by` 值本身即為可追溯引用（`tarrragon/claude#23` 可直接 `gh issue view`） | 無 |
| 與現有 20 張票的填法完全相容 | 無 |

### 方案 B：守衛分類輸出，框架升級關閉列為 INFO

**做法**：L381 命中時，進一步檢查是否符合 `owner/repo#N` 格式；符合則輸出 INFO（非 anomaly），不符合才列為異常。

| 利 | 弊 |
|----|-----|
| 保留守衛對真正異常值的偵測能力 | 改動較大，需重構 anomalies 輸出結構（目前只有單一 list） |
| INFO 輸出讓使用者知道有框架關閉的票 | 20 張 INFO 仍是噪音（只是降級，未消除） |

### 方案 C：改填法為本地 ticket ID，框架 issue 記在 body

**做法**：規範 `closed_by` 只填本地 ticket ID 或 `none`；框架 issue 引用移到 `close_reason_note` 或 body。

| 利 | 弊 |
|----|-----|
| 守衛無需修改 | 可稽核性降低——`closed_by` 無法直接追回框架 issue，需額外翻 body |
| | 需修改 20 張已完成票的 frontmatter（違反 tool-output-trust 規則 6：以過期判準反向修改正確產出） |
| | `closed_by` 填本地 ticket ID 語意不通——票是被框架 issue 關閉的，不是被另一張本地票關閉的 |

### 推薦方案

**方案 A**。理由：

1. 最小改動，精確解決問題
2. 不需修改 20 張已完成票（符合 tool-output-trust 規則 6）
3. 可稽核性最佳——`closed_by: tarrragon/claude#23` 本身就是可追溯引用
4. 方案 B 的 INFO 分級增加了不必要的複雜度（守衛目前不分級），且 20 行 INFO 仍是噪音
5. 方案 C 語意錯誤且需回溯修改

### 配套：建立端規範缺口修補

`framework-issue/SKILL.md` 路徑 A 應補充 `closed_by` 填法規範：「以框架 issue 關閉本地 ticket 時，`closed_by` 填 `owner/repo#N`（如 `tarrragon/claude#23`）」。此為同一上游修復的一部分。

### 與 W2-043 的相容性

W2-043 定案結論：`.claude/` 本地修改會被 sync-pull 覆蓋，修復落點在上游。本票結論完全相容——方案 A 的修改標的（`version-tracking-consistency-guard-hook.py`）和配套（`framework-issue/SKILL.md`）皆位於 `.claude/`，修復同樣須在上游 `tarrragon/claude` 執行。
