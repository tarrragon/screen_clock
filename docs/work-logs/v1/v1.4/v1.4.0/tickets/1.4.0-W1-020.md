## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

SPEC-007 FR-03（104 行）約束條件明確描述：「被綁定鍵的 `otherMouseDown` / `otherMouseUp`：**回呼回傳 `nil` 消費事件**」——即綁定鍵的按下與放開兩個事件都應被消費。

但 `macos/Runner/MainFlutterWindow.swift` 的 `handleButtonUp`（669 行）實作邏輯為：

```swift
private func handleButtonUp(event: CGEvent) -> Unmanaged<CGEvent>? {
    if draggingAction != nil {
        draggingAction = nil
        return nil           // 僅 DragScroll：消費
    }
    return Unmanaged.passUnretained(event) // 其餘（含 Hotkey）：放行
}
```

直接原因：`handleButtonUp` 僅以 `draggingAction != nil` 判定是否消費 mouseUp。Hotkey 綁定在 `handleButtonDown`（478 行）合成鍵盤事件後不設定 `draggingAction`，故對應的 mouseUp 一律通過 tap 放行至底層應用。

### 影響範圍

| 範圍 | 說明 |
|------|------|
| 受影響綁定類型 | 僅 Hotkey（`type == "hotkey"`）；DragScroll 不受影響 |
| 受影響事件 | `otherMouseUp`（`handleButtonUp` 回傳原事件而非 nil） |
| 涉及檔案 | `macos/Runner/MainFlutterWindow.swift`（669-675 行） |
| 規格落差 | SPEC-007 FR-03（116 行）、FR-05（169 行引用 FR-03 消費語意） |
| 文件已反映實作 | UC-05 主要場景步驟 4（62 行）與已知限制（126 行）如實描述了放行行為 |

已驗證事實：DragScroll 綁定的 mouseUp 被正確消費（`draggingAction` 狀態驅動）。
仍未驗證假設：穿透的 orphan mouseUp 在主流 macOS 應用中是否造成可觀察的使用者後果（見重現實驗結果章節）。

## 重現實驗結果
### 實驗方法

以靜態程式碼路徑追蹤為主，逐一追蹤 CGEventTap 回呼對 Hotkey 綁定 mouseDown/mouseUp 的回傳值，驗證消費條件與 SPEC FR-03 的一致性。

輔以 macOS 平台行為分析：評估 orphan otherMouseUp（無對應 mouseDown 的 mouseUp 事件）到達底層應用時的實際後果。

本實驗不含實機按鍵操作（SA 唯讀分析限制），使用者可感知後果的判定依據為 macOS 事件處理架構特性。

### 實驗執行

#### 路徑 A：DragScroll 綁定（對照組——行為符合 SPEC）

| 步驟 | 程式碼位置 | 回傳值 | 消費？ |
|------|----------|--------|--------|
| otherMouseDown → handleButtonDown | 473-476 行 | `nil`（設 `draggingAction = action`） | 是 |
| otherMouseUp → handleButtonUp | 670-672 行 | `nil`（`draggingAction != nil` 成立，清除拖曳狀態） | 是 |

結論：DragScroll 的 down/up 皆回傳 nil，兩事件皆被消費。符合 SPEC-007 FR-03。

#### 路徑 B：Hotkey 綁定（實驗組——行為偏離 SPEC）

| 步驟 | 程式碼位置 | 回傳值 | 消費？ |
|------|----------|--------|--------|
| otherMouseDown → handleButtonDown | 478-481 行 | `nil`（呼叫 `synthesizeHotkey` 後消費） | 是 |
| otherMouseUp → handleButtonUp | 670 行 `draggingAction != nil` → false → 674 行 | `Unmanaged.passUnretained(event)` | **否，放行** |

結論：Hotkey 綁定的 mouseDown 被消費，但 mouseUp 未被消費而穿透至底層應用。

#### 路徑 C：使用者可感知後果分析

mouseDown 已被消費，底層應用僅收到一個 orphan otherMouseUp（無對應 mouseDown）。分析此 orphan mouseUp 是否造成誤觸發：

| 應用類型 | otherMouseUp 處理方式 | 誤觸發風險 |
|---------|---------------------|-----------|
| 瀏覽器 (Safari/Chrome/Firefox) | 側鍵 back/forward 由 mouseDown 觸發；orphan mouseUp 無對應 mouseDown tracking state，被 NSResponder chain 忽略 | 低（不觸發導覽） |
| Finder | 同上，側鍵導覽基於 mouseDown | 低 |
| NSResponder 預設實作 | `otherMouseUp:` 預設沿 responder chain 傳遞，無 handler 時安靜丟棄 | 無 |
| 自訂 otherMouseUp handler 的應用 | 理論上可能回應 orphan mouseUp，但須該應用特別實作 otherMouseUp 且不依賴 mouseDown 狀態配對 | 極低（非典型設計） |

macOS 事件模型觀察：AppKit 的 NSResponder 對 otherMouse 事件的預設行為是沿 responder chain 傳遞，大多數應用不覆寫 `otherMouseUp:`。側鍵的 back/forward 導覽由 mouseDown 驅動，mouseUp 不獨立觸發動作。

### 實驗發現

**已驗證事實**：

1. `handleButtonUp` 的消費條件僅檢查 `draggingAction != nil`，不區分 binding type
2. Hotkey 綁定的 `handleButtonDown` 不設定 `draggingAction`（設計正確——Hotkey 無拖曳狀態）
3. Hotkey 綁定的 mouseUp 放行是 handleButtonUp 未追蹤 "已消費 buttonDown" 狀態的直接結果
4. 未設定追蹤變數（如 `consumedButtonDown: Set<Int64>`）來記錄哪些按鍵的 mouseDown 已被消費

**使用者後果判定**：

穿透的 orphan mouseUp 在當前主流 macOS 應用中**不造成可觀察的誤觸發**。原因：macOS 側鍵導覽（back/forward）由 mouseDown 驅動，mouseDown 已被消費；orphan mouseUp 被 NSResponder 預設機制安靜丟棄。

但此為**實作缺陷而非可接受行為**——SPEC-007 FR-03 的 "otherMouseDown / otherMouseUp 回呼回傳 nil 消費事件" 是防禦性規格：即使當前主流 app 不回應 orphan mouseUp，未來 app 或 macOS 版本的行為不保證一致。PROP-002 "一律吃掉為使用者明確選擇"（157 行）表達的意圖是完整消費，不依賴下游 app 的忽略行為。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 判定結論

**SPEC-007 FR-03 描述為正確意圖；實作存在缺陷。**

判定依據：

1. **PROP-002 原始意圖**：「一律吃掉為使用者明確選擇」（157 行）——使用者綁定按鍵即表示放棄該鍵的所有原始行為，消費應涵蓋 down 與 up
2. **SPEC-007 FR-03 規格明確**：「被綁定鍵的 `otherMouseDown` / `otherMouseUp`：回呼回傳 nil 消費事件」（116 行）——不分 binding type，兩事件皆消費
3. **實作邏輯缺口**：`handleButtonUp` 僅以 `draggingAction` 狀態判定消費，缺少對 Hotkey 綁定的消費路徑
4. **使用者後果**：當前主流 app 不因 orphan mouseUp 誤觸發（低風險），但不消費的行為違反 SPEC 防禦性意圖，且未來 app/OS 行為不保證

### 候選方案

#### 方案 A：修正 Swift 實作對齊 SPEC（建議採用）

在 `handleButtonUp` 中新增對 Hotkey 綁定的消費邏輯。實作策略：

1. 新增狀態變數 `consumedButtonDown: Set<Int64>`（或 `Int64?`，因一次僅一個 button 按下）
2. `handleButtonDown` 的 hotkey 分支在消費 mouseDown 時記錄 button number
3. `handleButtonUp` 檢查釋放的 button 是否在 `consumedButtonDown` 中，若是則消費並移除

利：SPEC-實作一致；防禦性消費完整；DragScroll 邏輯不受影響（draggingAction 分支優先）
弊：新增一個狀態變數；需考慮邊界條件（同時按多個側鍵時的 Set 管理）

#### 方案 B：修正 SPEC FR-03 文字降級為僅承諾 mouseDown 消費

將 FR-03 約束條件改為「被綁定鍵的 `otherMouseDown`：回呼回傳 nil 消費事件；`otherMouseUp` 依動作類型決定是否消費」。

利：不需改程式碼；文件對齊實作
弊：降低防禦性（orphan mouseUp 放行成為規格允許的行為）；違反 PROP-002 「一律吃掉」的原始意圖；若未來 macOS 或某應用在 mouseUp 上加入行為，需重新修正

### 建議

採方案 A。修正量小（約 10 行 Swift），風險低，且與 PROP-002/SPEC-007 的原始意圖一致。
