## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

1.4.0-W3-018 的 `testGeometrySyncDoesNotStartImplicitAnimation` 沿用了
1.4.0-W3-021 早期已知失效的實測手法（以 `animationKeys()` 為空作為隱含動畫未啟動的
斷言），但該手法在 1.4.0-W3-021 過程中已被證實需要特定宿主條件（獨立宿主 + 幀間
`CATransaction.flush()`）才具分辨力。W3-018 撰寫當下未執行 RED 對照驗證，只是沿用
同一斷言型式套用在真實 `WindowCursorLocatorSurface` 上，未確認該宿主是否滿足分辨力
所需條件。影響範圍僅限本測試（`macos/RunnerTests/CursorLocatorSurfaceContractTests.swift`
第 149-163 行），不影響其他測試或 production 程式碼正確性。

### 影響範圍

- 已驗證的事實：`testGeometrySyncDoesNotStartImplicitAnimation` 目前對隱含動畫破壞
  無回歸保護能力（見「重現實驗結果」）。
- 已驗證的事實：`macos/RunnerTests/` 內唯二使用 `animationKeys` 的測試檔為
  `CursorLocatorEffectCompositionTests.swift`（W3-021 手法，已驗證有效）與
  `CursorLocatorSurfaceContractTests.swift`（本票標的，已驗證無效）。
- 仍未驗證的假設：production 程式碼 `LayerHostingView.synchronizeHostedLayer` 的
  `CATransaction.setDisableActions(true)` 本身是否正確運作——本票僅驗證「測試是否
  能偵測其被移除」，不對 production 行為做額外斷言。

### 相關 Error Pattern

未執行 `/error-pattern query`（本票為既有 W3-021 教訓的延伸複查，非新錯誤模式；
若後續 IMP 票修復後仍反覆出現空斷言問題，屆時再評估是否需建立獨立 error-pattern）。

## 重現實驗結果
### 實驗方法

RED 對照法（沿用 1.4.0-W3-021 已驗證有效的實測手法）：暫時移除
`LayerHostingView.synchronizeHostedLayer`（macos/Runner/CursorLocatorEffectWindow.swift）
內的 `CATransaction.setDisableActions(true)`，執行
`CursorLocatorSurfaceContractTests.testGeometrySyncDoesNotStartImplicitAnimation`，
觀察該測試是否轉紅。若轉紅代表測試具分辨力（無問題）；若仍為綠燈代表測試對隱含動畫
無感知，屬空斷言。

指令：
```
xcodebuild test -workspace macos/Runner.xcworkspace -scheme Runner \
  -configuration Debug -destination 'platform=macOS' \
  -only-testing:RunnerTests/CursorLocatorSurfaceContractTests/testGeometrySyncDoesNotStartImplicitAnimation
```

### 實驗執行

第一輪（移除 disableActions，不加額外 flush）：
- 修改 `synchronizeHostedLayer` 移除 `CATransaction.setDisableActions(true)`
- 執行測試 -> **TEST SUCCEEDED**（`testGeometrySyncDoesNotStartImplicitAnimation() passed (0.010 seconds)`）
- 結果：未轉紅

第二輪（同上，額外在測試內 `surface.move(toScreenFrame: moved)` 後加
`CATransaction.flush()`，比照 1.4.0-W3-021 composition 測試在寫入後 flush 的手法，
排除「未 commit 到 render context」這個混淆變因）：
- 執行測試 -> **TEST SUCCEEDED**（`testGeometrySyncDoesNotStartImplicitAnimation() passed (0.031 seconds)`）
- 結果：仍未轉紅

兩輪實測後已還原全部暫時修改（`git diff --stat macos/` 確認為空），並執行
`scripts/run-tests.sh` 全量驗證，flutter test 與 xcodebuild test 皆通過（含
CursorLocatorSurfaceContractTests 全數 GREEN）。

附帶掃描：`grep -rln "animationKeys" macos/RunnerTests/*.swift` 僅命中
`CursorLocatorEffectCompositionTests.swift`（用 1.4.0-W3-021 已驗證有效的
`makeHostedLayer` 手法：獨立 layer-hosted `NSView` + 幀間 `CATransaction.flush()`）
與 `CursorLocatorSurfaceContractTests.swift`（本票標的）。宿主環境已逐一確認，無其他
倚賴 CoreAnimation 副作用斷言的測試需要複查。

### 實驗發現

**已驗證的事實**：`testGeometrySyncDoesNotStartImplicitAnimation` 為空斷言——移除
受測程式碼的隱含動畫防護（`CATransaction.setDisableActions(true)`）後，該測試仍維持
GREEN，無論是否額外補 `CATransaction.flush()` 皆同。即使該測試使用真實
`WindowCursorLocatorSurface`（含 `NonKeyEffectWindow` 並於 `init` 呼叫
`orderFrontRegardless()`，比 1.4.0-W3-021 最初失敗版本的裸宿主更「真實」），仍無法
使 `animationKeys()` 觀察到隱含動畫被啟動。

**仍未驗證的假設**：確切原因未深究（可能是 XCTest 執行環境下 window server
連線狀態、或需要額外的 run loop 迭代讓 CVDisplayLink 真正連上 render context，
與 1.4.0-W3-021 composition 測試用的獨立 `NSView`（無 `orderFront`，僅單次
`CATransaction.flush()` 建立初始 commit）在連線時機上有差異）。本票範疇僅要求確認
是否具分辨力，不要求根因定位；根因與具體修法留給衍生的 IMP 票（見 Solution）。

**結論**：1.4.0-W3-018 的隱含動畫防護目前**沒有回歸保護**——若未來有人移除或破壞該
`CATransaction` 防護，此測試不會發現。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 結論

`testGeometrySyncDoesNotStartImplicitAnimation` 為空斷言，已建立衍生 IMP 票
`1.4.0-W3-027` 補強宿主環境。本票不修改 production 程式碼或測試碼（僅執行 RED 對照
實測，實測後已還原全部暫時改動）。

### 候選方案（供 1.4.0-W3-027 參考）

| 方案 | 做法 | 利 | 弊 |
|------|------|-----|-----|
| A（採用） | 比照 `CursorLocatorEffectCompositionTests.makeHostedLayer` 手法，重寫本測試改用獨立 layer-hosted `NSView` + 幀間 `CATransaction.flush()`，不再依賴 `WindowCursorLocatorSurface` 的完整 production 初始化流程 | 已在 1.4.0-W3-021 驗證有效；改動範圍侷限在單一測試檔 | 測試不再直接驗證 `WindowCursorLocatorSurface.move()` 真實路徑，需額外斷言 `synchronizeHostedLayer` 邏輯有被觸發到 |
| B | 深究根因（run loop 迭代 / window server 連線時機），修正 production 或測試以在真實 `WindowCursorLocatorSurface` 上也能生成可觀察的隱含動畫 | 測試維持覆蓋 production 真實路徑，分辨力更貼近實際風險 | 根因未知，可能需要較長時間調查；若根因是 XCTest 環境限制（如無 window server session），可能無法在測試環境內复現，方案不可行 |

推薦方案 A：1.4.0-W3-021 已證實此手法有效，可直接複用，不需承擔方案 B 的根因未知
風險；缺點（不直接測 production 真實路徑）可透過額外斷言
`hostView.synchronizeHostedLayer()` 或等效行為有被呼叫到來緩解，留給 1.4.0-W3-027
實作時決定。
