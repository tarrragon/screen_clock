## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

settings.json 是框架分發物（由 tarrragon/claude 上游維護），sync-pull 執行三方合併時以上游為權威來源全量覆蓋。W2-029 的修復（c720029, 刪 15 行）僅作用於本專案 working tree，未上推至上游。下一次 sync-pull（ee7e6af, 2026-08-05）從上游拉取時，上游仍含三個被合併 hook 的註冊，三方合併將其加回。

直接原因：本地 delta 與上游不同步，sync-pull 無 settings.json 欄位級 merge 或排除機制。
根本原因：settings.json 的角色定位為「框架 Hook 註冊表」（session-start-sync-exclusion-check-hook 明確將其歸類為 _FRAMEWORK_CONFIG，不加入 LOCAL_ONLY_PATTERNS），因此 sync 設計上預期它完全由上游控制——本地修正本就不該停留在 settings.json。

### 影響範圍

已驗證事實：
- c720029（2026-07-31）刪除 changelog-update-hook / commit-handoff-hook / post-commit-fetch-hook 三處註冊（行 547/557/567，共 15 行）
- ee7e6af（2026-08-05）sync-pull 從上游 7c604cbaed36 拉入，三處註冊全數加回（行 587/592/597）
- 當前 grep 實測確認三處仍存在
- 影響：每次 commit 後三個已被合併的 hook 各執行一次（與合併版 post-git-commit-hook 重複），加劇 index.lock 競爭

未驗證假設：
- 上游 tarrragon/claude 的 settings.json 是否仍含這三處註冊（高度可能，因 sync-pull 帶回即為上游狀態）

### 相關 Error Pattern

無直接對應的已知 error-pattern。本問題屬框架層級的 sync 機制設計缺口（框架分發物與專案本地修正的持久性衝突），非 process-compliance 或 implementation 錯誤。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 分析結論

W2-029 的修復落點錯誤：修復作用於下游消費者（本專案的 settings.json），而問題根源在上游（tarrragon/claude 的 settings.json 仍註冊已被合併的 hook）。正確做法是修復上游，讓所有下游消費者自動受益。

### 候選方案比較

| 方案 | 描述 | 優點 | 缺點 | 評估 |
|------|------|------|------|------|
| **(a) 修復上推上游** | 在 tarrragon/claude 上游移除三個被合併 hook 的註冊，下次 sync-pull 自動同步至所有消費者 | 一次修復、永久生效；所有消費者專案受益；符合 settings.json 作為框架設定檔的角色定位；零本地 delta | 需操作上游 repo；修復到下游生效有時間差（下次 sync-pull） | **推薦** |
| (b) settings.local.json 承載本地覆寫 | 將三個 hook 的移除放入 settings.local.json（Claude Code 支援 local override） | 不依賴上游修復時程 | settings.local.json 為 permission + MCP 配置層，非 Hook 註冊層——Claude Code 的 hook 合併語意不明確（可能是 union 而非 override）；即使能 override，仍需每個消費者專案各自維護本地覆寫；上游問題未修仍會持續影響新 onboard 的專案 | **不推薦** |
| (c) sync-pull 欄位級 merge / 排除清單 | 在 sync-pull 流程中加入 settings.json 的欄位級 merge 邏輯或 hook 排除清單 | 可處理任意本地 delta | 過度工程——settings.json 的設計定位就是框架控制，加欄位級 merge 等於否定這個定位；維護成本高（每次上游新增 hook 都要處理 merge conflict）；不解決根本問題（上游仍有錯誤註冊） | **不推薦** |

### 評估軸分析

| 評估軸 | 方案 a | 方案 b | 方案 c |
|--------|--------|--------|--------|
| 本地 delta 是否需跨專案共用 | 是（所有用此框架的專案都受影響） | 否（每專案獨立）| 否 |
| sync 頻率與覆蓋後偵測時效 | 修復後不再被覆蓋 | 每次 sync-pull 需確認 override 仍有效 | 每次 sync-pull 需維護 merge 規則 |
| 覆蓋後偵測能力 | hook-completeness-check（W2-029 擴充）在 session-start 自動偵測 | 同左 | 同左 |
| 與 settings.json 角色定位一致性 | 完全一致（框架檔由上游控制） | 部分衝突 | 嚴重衝突 |

### 結論

**W2-029 的修復應重新套用於上游 tarrragon/claude**（方案 a）。具體步驟：
1. 在上游 repo 移除 changelog-update-hook / commit-handoff-hook / post-commit-fetch-hook 三個 hook 的 settings.json 註冊
2. 同時處理 dart-style-guardian-hook 在 Write matcher 下的重複註冊（不帶參數的版本應移除）
3. 下次 sync-pull 自動同步修復至所有消費者專案
4. 本專案在上游修復到位前，可暫行本地刪除以止血（但需理解下次 sync-pull 前若上游未修仍會回歸）

### 框架層 vs 專案層判定

本問題屬**框架層**。依據：
- settings.json 由 tarrragon/claude 上游維護，是框架分發物
- 問題根源是上游的 hook 註冊未隨合併事件同步清理
- 修復應作用於上游，影響所有消費者專案
- 符合 `.claude/skills/framework-issue/SKILL.md` 的框架問題定義：「替換專案名稱和檔案路徑後仍有意義」
