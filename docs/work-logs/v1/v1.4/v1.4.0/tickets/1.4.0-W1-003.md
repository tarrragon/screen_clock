## Context Bundle

### 規範依據

- .claude/skills/doc/doc_system/core/tracking_schema.py — PROPOSALS_TRACKING_SCHEMA 是權威 schema（建立端），本 ticket 依它改寫資料
- .claude/skills/doc/references/tracking.md — tracking 規範描述層

注意兩者不一致時的判定順序：canonical 常數（tracking_schema.py）優先於文件描述（tracking.md）。references/tracking.md 的範例仍用舊的 dict-keyed 格式與 confirmed 欄位名，那是待同步的下游描述，不可據以改寫資料。此判定依 .claude/rules/core/tool-output-trust-rules.md 規則 6。

### 現況證據

doc status 輸出：提案總數 0（實際 docs/proposals-tracking.yaml 有 3 個提案）。原因為現有格式是 dict-keyed-by-id，新 schema 要求 list。

### Schema 差異對照

| 面向 | 現況（舊） | 目標（PROPOSALS_TRACKING_SCHEMA） |
|------|-----------|----------------------------------|
| 頂層 key | 僅 proposals | proposals / usecases / specs 三個 |
| proposals 結構 | dict，key 為 PROP-NNN | list，每個 entry 含 id 欄位 |
| entry 必填 | 無明確定義 | id / title / status |
| 確認日期欄位名 | confirmed | confirmed_at |
| entry 選填 | — | priority / completed_note / target_version / proposed / source / spec_refs / usecase_refs / ticket_refs / checklist / canonical_ssot / tracking_ticket / depends_on |

usecases 與 specs 兩個新頂層 key 的 entry 結構未在 schema 常數中明確定義必填欄位；建立時採最小可用形式（id + title + status + 指向檔案路徑），並在 ticket 的 Solution 章節記錄所採結構與理由。

### 狀態校準（第二項職責）

現有 tracking 的提案狀態與實際發布進度脫節，須依 docs/todolist.yaml 的版本完成狀態校準：

| 提案 | target_version | 版本實際狀態 | 應校準為 |
|------|---------------|-------------|---------|
| PROP-001 | v0.1.0（實際跨 v0.1.0 至 v1.0.0） | 已發布 | 依 checklist 逐項核對後判定 implemented 或 confirmed |
| PROP-002 | v1.3.0 | 已發布 | 同上 |
| PROP-003 | v1.4.0 | 進行中（active） | confirmed（已進入實作規劃） |

checklist 每項的 verified_by 須填實際完成該項的 ticket ID。查法：ticket track list --all 逐版本比對，或 grep docs/work-logs/ 下 ticket 的 what 欄位。查不到對應 ticket 的項目，verified_by 留 null 並在 Solution 記錄，不虛構 ticket ID。

### 執行約束

- 不改變任何提案的實質內容（title / target_version / checklist item 文字維持原樣）
- spec_refs 路徑須用 1.4.0-W1-002 重命名後的新路徑（本 ticket blockedBy W1-002，執行時該重命名已完成，須先 ls docs/spec/ 確認實際檔名）
- 狀態校準以版本發布事實為依據，非以感覺推測；判定依據寫入 Solution 章節
