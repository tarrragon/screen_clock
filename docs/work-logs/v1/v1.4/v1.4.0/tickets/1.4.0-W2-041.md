### 為何新增獨立案例（而非只信賴既有 T2.C-05）

反向驗證（見 Test Results）意外發現：既有 T2.C-05
(`testPlay_afterReset_newDurationCountsFromResetPoint`) 在「重置分支遞增世代
序號」的 bug 注入下**已會轉紅**（因其結尾斷言 `.idle`，而幀被世代 guard 攔死
會使狀態永久停在 `.playing`）。這與母票敘述的「現有測試設計無法捕捉此缺陷」
表面不一致；但 T2.C-05 的紅燈是**間接**訊號（只在「最終有沒有到 idle」處爆
出），無法定位問題出在「重置後的幀」還是其他路徑，且其設計初衷是驗證
「重置後時間重新起算」而非「重置後 driver 是否持續供幀」，兩者恰好用同一組
斷言把後者間接覆蓋，屬巧合而非設計意圖。

新案例的設計價值：逐幀直接斷言 elapsed 推進與 alpha 寫入，紅燈訊息會精確
指向哪一幀、哪個欄位失效（見反向驗證輸出），縮短未來真的復發時的除錯路徑；
同時案例名稱與註解明示「這是重置後 driver 供幀的專屬回歸測試」，補上母票
所述「Phase 2 群組 C 未涵蓋跨重置時序」在意圖表達層的缺口。

### 案例設計

play(duration 1.5) → 推進 2 幀（elapsed 0, 0.6）→ 再次 play(duration 1.0，觸發
重置）→ 推進 4 幀，逐一斷言：
- 重置當下 elapsed 立即歸零（沿用既有慣例）
- 重置後兩幀 elapsed 確實線性推進（0.1、0.3，非凍結於 0）
- 進入淡出窗（fadeStart=0.8）後 alpha 確實有新寫入（`alphaValues.count > 1`
  且新值 < 1.0），排除「只剩重置當下 setAlpha(1.0) 一筆」的靜默丟棄情形
- 最終能自然抵達 `.idle` 且 `closeCount == 1`

沿用既有慣例：`ManualFrameDriver` 注入固定基準時間戳、`SurfaceCallLog` 觀測
`alphaValues`、零 wall clock、零 `XCTestExpectation`。

### 本票要守住的東西

`1.4.0-W2-006.2.1` 實作時發現並修正了 Phase 3a 虛擬碼的一個錯誤：**play 的重置分支不得遞增世代序號**。本票補上守住該決定的測試。

完整論證見母票 `1.4.0-W2-006` 的 Solution「Phase 3a 虛擬碼修正：重置分支不得遞增世代序號」節。摘要：

| 位置（`macos/Runner/CursorLocatorEffectWindow.swift`） | 事實 |
|------|------|
| 287-291 | `driver.start()` 時 `generation += 1`，`let capturedGeneration = generation` 由 closure 捕獲**值** |
| 303-328 `resetExistingPlayback` | 只呼叫 `frameDriver.retarget(displayID:)`，**不呼叫 `start()`** |
| 333 | `guard frameGeneration == generation else { return }` |
| 419 | 結束子程序 `generation += 1` |

若重置時遞增，driver closure 持有的世代永久落後，line 333 的 guard 自此永遠不成立——重置後所有幀被靜默丟棄，但 `state` 仍為 `.playing`。無異常、無日誌、無崩潰，只有畫面不再更新。

程式碼 line 196-202 已有完整註解說明此設計，本票的測試是該註解的機械執法層。

### 缺口性質

此缺陷由執行者反事實推理發現，**非測試紅燈觸發**。Phase 2 設計的群組 C（19 案例）皆在單次 driver 生命週期內驗證，無一跨越重置。現況是：若有人依原虛擬碼把重置分支改回遞增，43 個 XCTest 全數通過。

### 現有測試的模式（沿用，勿另立新風格）

`macos/RunnerTests/CursorLocatorEffectControllerLifecycleTests.swift`（388 行，群組 C）已建立的慣例：

- 時間推進一律由 `ManualFrameDriver` 注入固定基準時間戳，零 wall clock、零 `XCTestExpectation`
