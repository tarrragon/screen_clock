#### 1. Purpose

讓 `play` 呼叫能在「游標當下所在的螢幕」建立唯一一個特效視窗、播放固定時長後確實釋放，且整條路徑的判定邏輯與生命週期狀態不依賴 AppKit 全域狀態即可被 XCTest 斷言。核心設計原則：**把「決定在哪播」與「決定播多久／播幾個」抽成純資料運算，把「真的開視窗」隔在協定後面**，使 acceptance 1/2/4/5 有自動訊號，只留視窗 level 與視覺跟隨走實機驗證。

#### 2. API Signatures

##### 2.1 螢幕判定（子票 .1）

螢幕判定不接收 `NSScreen.screens` 全域，改由呼叫端注入，並以協定抽掉對 `NSScreen` 具體型別的依賴：

```swift
/// 參與游標命中判定所需的最小螢幕幾何資訊。
/// NSScreen 於 production 符合本協定；XCTest 以 struct 定樁螢幕排列。
protocol CursorHitTestableScreen {
  var hitTestFrame: NSRect { get }
}

extension NSScreen: CursorHitTestableScreen {
  var hitTestFrame: NSRect { frame }
}

/// 判定結果。以型別區分「命中」與「退回 main」，
/// 使呼叫端無須再比對回傳值即可決定是否記錄 E_CL_SCREEN。
enum CursorScreenResolution<Screen: CursorHitTestableScreen>: Equatable where Screen: Equatable {
  /// 找到 frame 涵蓋游標的螢幕（SPEC-008 FR-02 正常路徑）。
  case matched(Screen)
  /// 無涵蓋螢幕，退回 main（EX-06-02 復原路徑，呼叫端須記 E_CL_SCREEN）。
  case fellBackToMain(Screen)
  /// 連 main 都取不到（無可用螢幕）。呼叫端視為不可播放。
  case unavailable
}

enum CursorScreenLocator {
  /// 純函式：不讀取任何全域狀態，輸出只由三個參數決定。
  /// - screens: 依 NSScreen.screens 的原始順序傳入（命中取「第一個」依賴此順序）
  /// - mainScreen: NSScreen.main，可為 nil
  static func resolve<Screen: CursorHitTestableScreen & Equatable>(
    cursorLocation: NSPoint,
    screens: [Screen],
    mainScreen: Screen?
  ) -> CursorScreenResolution<Screen>
}
```

判定語意（Phase 2 須逐項出案例）：

| 條件 | 回傳 |
|------|------|
| 存在 `hitTestFrame` 涵蓋 `cursorLocation` 的螢幕 | `.matched(第一個命中者)`，順序即 `screens` 傳入順序 |
| 無涵蓋者且 `mainScreen != nil` | `.fellBackToMain(mainScreen!)` |
| 無涵蓋者且 `mainScreen == nil` | `.unavailable` |
| `screens` 為空但 `mainScreen != nil` | `.fellBackToMain(mainScreen!)` |
| 多個螢幕同時涵蓋（重疊排列） | `.matched(第一個)`，不做面積或距離仲裁 |

涵蓋判定採 `NSRect.contains(_:)` 的半開區間語意：`minX <= x < maxX`、`minY <= y < maxY`。故相鄰螢幕的共用邊界座標歸屬**該座標等於其 `minX`／`minY` 的那個螢幕**（語意等同 `NSPointInRect`），不會同時命中兩個，也不會兩個都不命中。此語意為契約的一部分，Phase 2 須有邊界座標案例鎖定（對應 §4 場景 3）。

> **PM 修訂（Phase 1.5，2026-07-31）**：本段原句為「故相鄰螢幕的共用邊界座標歸屬左／下側螢幕」，與自身的半開區間定義及 §4 場景 3 相反——代入 `[0,1920)` 與 `[1920,3840)`，x=1920 對前者為 `0 <= 1920 < 1920` 即 false、對後者為 `1920 <= 1920 < 3840` 即 true，故歸屬後者。原句由 linux 與 basil 兩個視角獨立指出，一致性視角的交叉檢查表則將此格誤判為「一致」。修訂改以 API 語意描述取代方向詞：方向隨座標系而變，`NSPointInRect` 的語意不變。教訓已記錄為 `PC-SCLK-006`。

```swift
  func close()
}

/// surface 工廠。production 實作建立 NSWindow 並設定 level、
/// collectionBehavior、ignoresMouseEvents（覆蓋假全螢幕，UC-06 06d）；
/// 建立失敗時 throw，觸發 E_CL_WINDOW 路徑。
protocol CursorLocatorSurfaceProviding {
  func makeSurface(screenFrame: NSRect) throws -> CursorLocatorSurface
}

/// 逐幀驅動。production 以 CVDisplayLink 實作；
/// 測試以手動 driver 推進時間，使「播放結束釋放」可確定性斷言，
/// 不使用 wall clock、不使用 expectation 等待（避免 flaky）。
protocol CursorLocatorFrameDriving: AnyObject {
  func start(onFrame: @escaping (TimeInterval) -> Void)
  func stop()
}

/// 游標位置取樣。production 讀 NSEvent.mouseLocation；
/// 測試以定樁座標序列驅動跨螢幕跟隨（UC-06 06a）。
protocol CursorLocationSampling {
  func currentLocation() -> NSPoint
}
```

每幀行為（`onFrame` 回呼內）：取樣游標位置 → 以 2.1 重新判定目標螢幕 → 目標螢幕與當前 surface 所在不同時呼叫 `move(toScreenFrame:)` → 累加 elapsed → `elapsed >= duration` 時停止 driver、`close()` surface、`activeSurfaceCount` 歸零、狀態回 `.idle`。播放中每幀的螢幕重判定即 FR-02 跨螢幕跟隨；重判定回 `.fellBackToMain` 時只記 log，不中斷播放。

##### 2.3 視覺特效的擴充點（本票不實作）

FR-03/04/05 三種特效各自實作以下協定，由 `CursorLocatorEffectController` 建構子以陣列注入。本票注入空陣列（或單一 no-op 實作）即可讓生命週期完整運作：

```swift
protocol CursorLocatorEffectRendering: AnyObject {
  func attach(to layer: CALayer, tint: NSColor, screenFrame: NSRect)
  func update(cursorLocation: NSPoint, elapsed: TimeInterval, duration: TimeInterval)
  /// 重複觸發時的重置（06b）：動畫進度回到起點，不重建圖層。
  func reset()
  func detach()
}
```

控制器對 renderer 的呼叫時機為契約：建立 surface 後 `attach`、每幀 `update`、重複觸發時 `reset`、釋放 surface 前 `detach`。Phase 2 可注入 spy renderer 斷言此序列，W3-001 據此接手即無須改動控制器。

##### 2.4 MainFlutterWindow.swift 的唯一改動

`CursorLocatorBridge` 持有一個 `CursorLocatorEffectController`，`handlePlay` 在既有參數解析成功之後，把 `NSLog + result(nil)` 換成委派：

```swift
do {
  try controller.play(CursorLocatorPlayRequest(duration: ..., tint: ...))
  result(nil)
} catch { /* 依 3. 錯誤路徑歸屬決定回傳 */ }
```

該檔不新增任何其他型別與職責（現 836 行，已超 cognitive-load 300 行閾值 2.8 倍）。channel 名／方法名／參數鍵沿用既有 `CursorLocatorChannel` enum，不重複定義。

#### 3. 錯誤路徑的介面歸屬

| 場景 | 錯誤碼 | 介面表現 | play 的 channel 回傳 |
|------|--------|---------|---------------------|
| 目標螢幕解析失敗（EX-06-02） | E_CL_SCREEN | `CursorScreenResolution.fellBackToMain`，控制器照常播放 | `result(nil)`，視為成功；僅 NSLog |
| 無任何可用螢幕 | E_CL_SCREEN | `.unavailable` → `throw .noAvailableScreen` | `result(FlutterError(code: "E_CL_SCREEN", ...))` |
| 特效視窗建立失敗（EX-06-03） | E_CL_WINDOW | 工廠 throw → `throw .windowCreationFailed` | `result(FlutterError(code: "E_CL_WINDOW", ...))` |
| 播放中每幀重判定退回 main | E_CL_SCREEN | 僅 NSLog，不中斷、不改變 state | 該次 play 早已回傳，無影響 |

依 Problem Analysis「規格落差澄清」：所有「回報 Dart 側」一律為本次 `play` 呼叫的同步 `FlutterError` 回應，**不新增原生至 Dart 的反向 channel 或 EventChannel**。`.fellBackToMain` 是 SPEC-008 錯誤處理表定義的復原路徑，不得以 FlutterError 中斷播放——這是本節與 acceptance 6 措辭的權威解讀差異點，Phase 2 須以「退回 main 時 play 仍 result(nil)」的案例鎖定。

`noAvailableScreen` 屬 SPEC-008 未列舉的殘餘情形（螢幕數為 0），歸入 E_CL_SCREEN 而非新增錯誤碼，避免擴張 SPEC 定義的錯誤碼集合。

#### 4. GWT 行為場景

- **場景 1（FR-02 正常判定）**：Given 兩個不重疊螢幕的定樁排列、游標座標落在第二個的 frame 內；When 呼叫 `resolve`；Then 回傳 `.matched(第二個螢幕)`。
- **場景 2（EX-06-02 間隙退回）**：Given 兩螢幕排列間存在未涵蓋座標、mainScreen 為第一個；When 以間隙座標呼叫 `resolve`；Then 回傳 `.fellBackToMain(第一個螢幕)`。
- **場景 3（邊界座標）**：Given 兩螢幕於 x=1920 相鄰；When 游標恰在 x=1920；Then 命中右側螢幕（半開區間語意），且僅命中一個。
- **場景 4（單次播放釋放）**：Given controller 為 idle、手動 frame driver；When `play(duration: 1.5)` 後推進時間至 1.5 秒；Then 過程中 `activeSurfaceCount == 1`，結束後 `== 0` 且 `state == .idle`。
- **場景 5（06b 重複觸發為重置）**：Given 播放進行至 elapsed 0.8；When 再次 `play`；Then `activeSurfaceCount` 維持 1、`state.elapsed` 歸零、spy renderer 收到 `reset()` 且未收到第二次 `attach()`。
- **場景 6（acceptance 5 無洩漏）**：Given 手動 driver；When 連續十次 `play` 並各推進至結束；Then 每次結束後 `activeSurfaceCount == 0`，十次結束時仍為 0。
- **場景 7（06a 跨螢幕跟隨）**：Given 游標取樣序列由螢幕 A 座標切至螢幕 B 座標；When 推進數幀；Then surface 收到 `move(toScreenFrame: B.frame)` 恰一次（同螢幕連續幀不重複搬遷）。
- **場景 8（EX-06-03）**：Given 注入必定 throw 的 surface 工廠；When `play`；Then 拋出 `.windowCreationFailed`、`activeSurfaceCount == 0`、bridge 以 `FlutterError(code: "E_CL_WINDOW")` 回傳。
- **場景 9（退回 main 不中斷）**：Given 游標落於間隙；When `play`；Then 正常建立 surface 於 main、play 回傳成功（非 FlutterError）。

#### 5. 邊界條件與約束

| 項目 | 契約 |
|------|------|
| `duration` <= 0 | 視為即時結束：建立 surface 後首幀即釋放，不 throw（Dart 側已由 FR-06 範圍 0.5~3.0 約束，原生層不重複驗證但須有定義行為） |
| `screens` 順序 | 命中取第一個，依賴傳入順序；production 直接傳 `NSScreen.screens` 不重排 |
| 同螢幕連續幀 | 不重複呼叫 `move`，避免每幀搬遷 |
| 不變量 | `activeSurfaceCount ∈ {0, 1}` 在所有公開方法前後皆成立 |
| `stop()` 於 idle | no-op，不 throw |
| 執行緒 | 所有公開方法假定於 main thread 呼叫（channel handler 與 CVDisplayLink 回呼須派回 main）；控制器本身不做鎖 |
| 純函式無全域 | `CursorScreenLocator.resolve` 不得讀 `NSScreen.screens` / `NSEvent.mouseLocation`，取樣責任在呼叫端 |
