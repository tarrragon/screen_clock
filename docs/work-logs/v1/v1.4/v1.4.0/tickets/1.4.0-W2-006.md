### 認領時 WRAP 三問（0.18.0-W10-027 checkpoint）

**W（Widen）—— 有其他做法嗎？**

Swift 側驗證策略列三個候選：(a) 啟用 XCTest 測純邏輯層（螢幕判定抽純函式 + 視窗生命週期以 controller 狀態機測）；(b) 純人工實機驗證，對齊專案現況（至今零 Swift 測試，RunnerTests 僅 scaffold 空殼）；(c) 只測螢幕判定純函式，生命週期全歸人工。用戶裁示採 (a)。理由：acceptance 5「重複觸發十次無視窗洩漏」在 (b)(c) 下無自動訊號，回歸防護完全依賴人工重跑；且 XCTest 基礎設施建立後 1.4.0-W3-001（三種視覺特效繪製）可直接複用。

**A（Attain distance）—— 機會成本是什麼？**

本票是 1.4.0-W2 唯一 P0，其餘 20+ 張 W2 票皆 P2（多為重構與文件同步）。執行本票擠壓的是 W2-015（拆分 MainFlutterWindow.swift 多 bridge 單檔累積）——但兩者實為互補而非競爭：本票依 cognitive-load 規則將特效視窗落於新檔 `macos/Runner/CursorLocatorEffectWindow.swift`，不再往 836 行的 MainFlutterWindow.swift 堆疊，等於減少 W2-015 屆時的拆分面。

**P（Prepare to be wrong）—— 最可能失敗的原因是什麼？**

最可能失敗點：XCTest target 接線。macos/RunnerTests 雖存在且 project.pbxproj 有 33 處 XCTest 引用，但從未實際執行過任何測試，`flutter test` 不涵蓋 Swift target，需經 xcodebuild 或 Xcode scheme 執行。若接線耗時超出預期，防護措施為：螢幕判定的純函式抽取與 NSWindow 生命週期實作本身不依賴測試框架就緒，可先落地實作再補測試執行路徑，避免 P0 票卡在基礎設施。

### 規格落差澄清：acceptance 6「回報 Dart 側」的語意

本票 acceptance 6 措辭為「螢幕解析失敗與視窗建立失敗皆有日誌並回報 Dart 側」，而 SPEC-008 介面規格節明載「原生層不主動回呼 Dart」。兩者不矛盾，但措辭易誤導，於此定義權威解讀：

- 「回報 Dart 側」指 `play` 這次 method channel 呼叫以 `result(FlutterError(code:message:details:))` 回傳錯誤，屬呼叫的同步回應，既有 CursorLocatorBridge 已具此路徑（MainFlutterWindow.swift:805 的參數缺失分支即為先例）
- **禁止**新增原生 → Dart 的反向 channel 或 EventChannel，該做法違反 SPEC-008 介面規格
- E_CL_SCREEN 依 SPEC-008 錯誤處理表為「退回 NSScreen.main」的**復原路徑**而非失敗路徑，故其「回報」限於 NSLog，不應以 FlutterError 中斷播放；僅 E_CL_WINDOW（視窗建立失敗、略過本次播放）走 FlutterError 回傳

### 檔案落點決策

新增 `macos/Runner/CursorLocatorEffectWindow.swift`，不將特效視窗程式碼加入 `MainFlutterWindow.swift`。

理由：MainFlutterWindow.swift 現為 836 行，超出 cognitive-load 規則的 300 行閾值 2.8 倍，且已承載時鐘遮罩視窗、CGEventTap、settings bridge、cursor locator bridge 等多個 domain，觸發「單一檔案承載 domain 數 > 2 必須拆分」條款。特效視窗的生命週期與上述任一 domain 皆無共用狀態，屬獨立 domain。MainFlutterWindow.swift 於本票僅改動一處：CursorLocatorBridge 的 play handler 由 NSLog 骨架改為委派至新類別。
