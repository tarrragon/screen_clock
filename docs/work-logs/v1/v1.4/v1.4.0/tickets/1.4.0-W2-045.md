### 建票後修正：缺陷 A 的前提被推翻（PM，2026-08-06 10:10）

本 ticket 的 why 將缺陷 A 記為「被拒的派發從未 spawn agent，記錄永久殘留」，此前提已被觀測推翻，須在分析中重新界定。

**觀測事實**：saffron-w2-042 完成後查 `.claude/dispatch-active.json`，剩餘筆數為 **0**（非預期的 1）。清理日誌顯示今日有 **兩次** SubagentStop：

```
[2026-08-06 10:05:00] SubagentStop fallback 清理（agent_id=a548f9be6881f7a11 無精準匹配，FIFO 清理最早 null entry）
[2026-08-06 10:08:32] SubagentStop fallback 清理（agent_id=asaffron-w2-042-0b515234894e9b8b 無精準匹配，FIFO 清理最早 null entry）
```

兩筆記錄各被一次 SubagentStop 清除，佇列歸零，未發生洩漏。

**對缺陷 A 的影響**：兩次 stop 事件帶有相異 agent_id，其中 `a548f9be6881f7a11` 非本 PM 顯式派發的任何 agent。這使原判定「第一筆記錄對應一次未 spawn 的被拒派發」失去支撐——若無 agent 被 spawn，不應有對應的 SubagentStop。至少存在三種未區分的解釋：(1) 被拒的 Agent 呼叫仍 spawn 了 agent，hook deny 僅阻止其收到任務；(2) 第一筆記錄對應的是本 session 其他來源（skill 或 hook）觸發的 agent，與被拒派發無關，兩者時間相近純屬巧合；(3) SubagentStop 與實際 agent 生命週期非一對一。

**對缺陷 B 的影響**：無。兩行日誌均明載「無精準匹配」，再次確證 by agent_id 的精準清理路徑從未命中，清理全靠 FIFO fallback。缺陷 B 維持原判定。

**分析須調整之處**：

1. 缺陷 A 應視為**待驗證假設**而非已確立事實。首要任務是查明 `a548f9be6881f7a11` 的來源，這決定 A 是否存在。
2. 原推論「計數永久偏移 1，每次被拒再加 1」不成立，本次已自癒歸零。缺陷 A 的實際後果須重新評估——若 FIFO 計數恆相符則無洩漏，僅在 stop 事件數與記錄數不等時才漂移。
3. 因此本 ticket 的優先級應在查明來源後重新評估；若 A 不存在，範圍收斂為缺陷 B 單一議題。
4. acceptance「現存的幽靈記錄已清理」已因佇列歸零而失去對象，應改為「幽靈記錄是否真實存在的判定」。

**方法論教訓**：原判定違反 tool-output-trust 規則 3——「記錄永久殘留」是從機制推論得出的預測，未以固定值命令驗證，卻被寫成已確立事實。可驗證而未驗證的推論不應進入 ticket 的 why。
