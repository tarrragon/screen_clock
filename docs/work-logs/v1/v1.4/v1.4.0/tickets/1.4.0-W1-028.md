新增 `macos/Runner/ButtonEventConsumption.swift`：獨立可測型別，追蹤「Hotkey 綁定 mouseDown 已消費的 button number」，供對應 mouseUp 比對消費。以 `struct` + `Set<Int64>`（而非單一 optional button）實作，理由：本 ticket 需要跨事件保存狀態（非既有四個先例的無狀態純函式），且需容忍多側鍵近乎同時按下的情境；`Set` 天然支援多 button 獨立追蹤，`recordHotkeyDownConsumed` / `consumeHotkeyUpIfMatched` 兩個 mutating 方法對應 down 記錄 / up 比對消費兩個決策點，消費後立即從 Set 移除（一次性配對）。

`InputBindingBridge`（`MainFlutterWindow.swift`）接線：
- 新增 `private var hotkeyConsumption = ButtonEventConsumption()` 實例屬性（與既有 `draggingAction` 並列）。
- `handleButtonDown` 的 hotkey 分支：`synthesizeHotkey` 後呼叫 `hotkeyConsumption.recordHotkeyDownConsumed(button:)`。
- CGEventTap 分派點（`handleTapEvent`）的 `.otherMouseUp` case：比照 `.otherMouseDown` 已有的做法，先取出 button number 再傳給 `handleButtonUp`（原本只傳 event，未取 button）。
- `handleButtonUp` 簽章改為 `(button: Int64, event: CGEvent)`：DragScroll 分支（`draggingAction != nil`）優先權不變（acceptance 2），其後新增 `hotkeyConsumption.consumeHotkeyUpIfMatched(button:)` 分支，命中則消費（`return nil`），否則放行。
- `teardownTap()` 新增重置 `hotkeyConsumption = ButtonEventConsumption()`，與既有重置 `draggingAction = nil` 對齊，避免 tap 重建後殘留舊 down 記錄。

新增 `macos/RunnerTests/ButtonEventConsumptionTests.swift`：5 個測試案例覆蓋核心狀態機行為（未記錄不消費／記錄後消費／一次性配對／不同 button 互不干擾／多 button 獨立追蹤），純函式無需實例化 MainFlutterWindow，不觸發 CGEventTap，符合 CLAUDE.md 已載明的無人值守執行風險約束。

Xcode 專案檔（project.pbxproj）補上兩個新檔的 PBXBuildFile / PBXFileReference / PBXGroup / PBXSourcesBuildPhase 條目（Runner target 掛 ButtonEventConsumption.swift，RunnerTests target 掛 ButtonEventConsumptionTests.swift），以 plutil -lint 驗證語法正確。

acceptance 2（DragScroll 既有消費行為不受影響）以程式碼審查驗證：draggingAction != nil 分支保持在最前面且邏輯字面未變動，只是新增其後的 else-if 分支；未新增獨立自動化測試，理由與既有 handleButtonDown/handleButtonUp 本身相同——這兩個函式依賴 CGEventTap 分派入口與實例狀態，無法脫離 InputBindingBridge 實例化測試（即 acceptance 3 前提章節所述的障礙），現況測試覆蓋停在可抽取的純函式邊界（ButtonEventConsumption）。

#### 現況程式碼（已定位）

`macos/Runner/MainFlutterWindow.swift`：

```swift
/// 側鍵放開：若正在拖曳則離開並消費，否則放行。
private func handleButtonUp(event: CGEvent) -> Unmanaged<CGEvent>? {
  if draggingAction != nil {
    draggingAction = nil
    return nil
  }
  return Unmanaged.passUnretained(event)   // ← Hotkey 綁定走此路徑，穿透
}
```

相關位置：`draggingAction` 宣告 295 行；事件 mask 383-384 行（down 與 up 皆在 mask 內）；分派 444 行 `.otherMouseDown` / 453-454 行 `.otherMouseUp`；`handleButtonDown` 的 Hotkey 分支 478-481 行（呼叫 `synthesizeHotkey` 後 `return nil` 消費）。

#### acceptance 條 3 的可測性前提（Phase 3a 須先解決）

acceptance 要求「XCTest 或 flutter test 覆蓋 Hotkey mouseUp 消費路徑」，但現況無法直接測：

| 障礙 | 說明 |
|------|------|
| `private func` | Swift 的 `@testable import` 只提升 internal 可見度，private 成員仍不可見 |
| 依賴實例狀態 | `draggingAction` 是 `MainFlutterWindow` 的實例屬性，測試需實例化該 window |
| 實例化即觸發 CGEventTap | `MainFlutterWindow` 啟動路徑會建立 event tap，無人值守執行時可能彈出輔助使用權限對話框而阻塞（CLAUDE.md 已載明此風險，`scripts/run-tests.sh` 檔頭註解亦有） |

因此把消費判定邏輯抽為獨立的可測型別是達成 acceptance 條 3 的前提，而非可選的重構。
