於 `.gitignore` 第 64 行、緊接既有 `.claude/dispatch-active.lock` 之後加入精確路徑 `.claude/error-patterns/.allocator.lock`。

### 規則形態選擇：精確路徑，不用通配（acceptance 條 1 要求說明理由）

`how.strategy` 要求評估是否改用 `.claude/**/*.lock` 通配一併涵蓋未來其他 skill 的鎖檔。**否決**，理由是查證發現 `.claude/` 下有必須版控的 `.lock` 檔：

```
$ git ls-files | grep "\.lock$"
.claude/hooks/uv.lock
.claude/skills/{doc,project-init,skill-sync,ticket,version-release,worktree}/uv.lock
macos/Podfile.lock
pubspec.lock
```

7 個 `uv.lock` 是 PEP 723 / uv 專案的依賴鎖檔，與 `Podfile.lock`、`pubspec.lock` 同屬「必須版控以確保可重現建置」的類別。通配規則會把它們納入忽略範圍。

雖然 gitignore 對**已追蹤**檔案無效（這 9 個目前不會因通配而被移出版控），但風險在未來：任一鎖檔若被刪除後重新加入，或新 skill 建立時，會被靜默忽略而不進版控，破壞建置可重現性。此類失效無明顯症狀，屬難偵測類別。

精確路徑的代價是未來其他 skill 的鎖檔需各自加行，但每次新增都是一次顯式決策，不會誤傷。

### 與 1.4.0-W1-029 的差異（acceptance 判準不可照抄）

本票建立時 acceptance 條 3 誤寫為「確認版控中已追蹤的 .lock 檔數維持為 0」，照抄自 W1-029（egg-info）的判準。執行時查證發現該判準對 `.lock` 不成立：

| 對象 | 是否應版控 | 「數量為 0」是否為正確判準 |
|------|-----------|------------------------|
| `*.egg-info/`（W1-029） | 全部不應 | 是 |
| `*.lock` | **混合**——依賴鎖檔應版控，執行期鎖檔不應 | 否，數量為 0 反而代表依賴鎖檔遺失 |

已將條 3 修正為「allocator.lock 未進入版控，且既有 9 個依賴鎖檔仍在版控中」——同時驗證「該忽略的被忽略」與「不該忽略的沒被誤傷」兩個方向。
