方案一，抽取共用MethodChannelMockHarness（如test/support/method_channel_mock_harness.dart）。利：未來若家族A出現第三消費者可直接複用，減少重複。弊：目前僅2個消費者，抽象層在家族B/C/D三種不同mock形態並存下難以泛化（會產生「看似共用實則只服務2個檔案」的假抽象），且會在兩個原本獨立的測試檔之間建立耦合（W2-005 R3-c原始判斷仍成立），與本票acceptance「若第三個消費者的mock需求形態不同則維持現狀」的分流條件相符。

### PM 驗收補正：移除無 trigger 的未來考量表述

原 Solution 於方案二「弊」欄含以下表述：

> 須留意未來若家族A新增消費者需重新評估（無需綁ticket，屬程式碼日常開發中自然會被注意到的重複，非需追蹤的技術債，故不建follow-up ticket）

**問題**：此句違反 `.claude/rules/core/decision-trigger-binding.md` 規則 1。ticket 作為載體只允許兩種狀態——(a) 已決策，或 (b) 綁定 ticket ID 的明確 trigger 延後；「須留意未來⋯需重新評估」屬第三種狀態（無 trigger 的未來考量），規則明文禁止。附帶理由「自然會被注意到」亦屬 `document-writing-style` 點名的隱含表達。

**為何該表述不成立**：重複程式碼被察覺的前提是有人在同一次改動中同時觸及兩處。本案兩個檔案分屬不同測試情境（`cursor_locator_test.dart` 與 `cursor_locator_hotkey_controller_test.dart`），可能長期不會被同一次改動涵蓋，「日常開發中自然注意到」缺乏機制支撐。

**補正後的結論狀態**：本票為純粹的狀態 (a) 已決策——不抽取共用 harness，關閉本票。理由為家族 A 維持 2 個消費者、4 種 mock 形態並存使全域抽象難以泛化、局部抽取收益低於耦合成本。

**未來若家族 A 出現第三個消費者**：屬當時的新發現，依 quality-baseline 規則 5「發現即建立，不詢問確認」於發現當下建立 ticket 處理，不需本票預留軟提醒。此為既有規則已覆蓋的路徑，非本票的未決事項。

**不影響原分析**：盤點資料、四家族分類、方案比較與結論本身均維持不變，本補正僅移除一處不合規的表述形態。
