在 `test/models/settings_model_test.dart` 新增群組「SettingsModel schema golden fixtures (1.4.0-W1-015, SPEC-009 A.1)」，含 4 個歷史 schema fixture 常數（v1/v2/v3-early/v3-late）+ 1 個 schema 4 骨架 fixture，及對應 5 個測試。

四組歷史 fixture 內容依 Context Bundle 指示，以 `git show <commit>:lib/models/settings_model.dart` 讀出各版 toJson() 實際欄位集構成（未依 SPEC 描述推測）：
- v1（bd83aea）：7 欄純量
- v2（afa3d67）：v1 + lifeTimerMode + birthDate
- v3-early（d05724a）：v2 + bindings（2 筆，drag scroll + hotkey），無 bindingsSeeded 鍵
- v3-late（10284df 起，const spread `{...v3EarlyFixture, 'bindingsSeeded': true}`）：v3-early + bindingsSeeded=true

v3-early 與 v3-late 為兩組獨立 fixture（schemaVersion 皆 3），差異僅 bindingsSeeded 鍵是否存在，各自測試驗證 `_migrateBindingSeed` 的兩個分支（缺鍵 fallback 字面 false / 存在時讀取真值）。

每組 fixture 逐欄位斷言（非僅物件相等）：純量欄位逐一 expect，bindings 逐筆檢查 buttonNumber/action 型別/內部欄位，bindingsSeeded 明確斷言其布林值，並額外用完整物件相等作交叉驗證。

**驗收條件 4（schema 4 fixture）處理方式**：採用 Context Bundle 提供的第二個選項「僅建立 fixture 常數而暫不加入斷言矩陣」的變體——由於 SPEC-009 A.1 明載 v4 三個新欄位的 JSON 鍵名於 1.4.0-W1-001 實作前不預先斷言（若貿然斷言不存在的 SettingsModel 欄位會導致編譯錯誤，而非單純測試失敗），改為：建立 v4Fixture（schemaVersion=4 + v3-late 全部欄位 + 3 個明確標註「佔位鍵名、非最終鍵名」的未知鍵），測試只斷言「現有 11 個既有欄位在 schemaVersion 升級與新增未知鍵時仍正確解析」，不斷言尚不存在的三個新欄位。此測試驗證 SPEC-008 FR-06 NFR-04（向後相容）的前置條件，待 1.4.0-W1-001 落地後於此測試補上三個新欄位的實際鍵名與逐欄位斷言、接線進矩陣（已於程式碼註解中明確記錄此 TODO 與理由）。

不修改 lib/ 下任何程式碼（驗收條件 3 的臨時實驗除外，已於 Test Results 記錄並還原，`git diff lib/models/settings_model.dart` 為空）。

### 四組 fixture 的界定（關鍵）

W1-011 確認 schema v3 存在兩種資料形態，因 bindingsSeeded 於 commit 10284df 加欄時未提升 schemaVersion：

| fixture | 內容 | 來源 |
|---------|------|------|
| v1 | 7 欄，無 lifeTimerMode / birthDate / bindings / bindingsSeeded | commit bd83aea 的 toJson 欄位集 |
| v2 | v1 + lifeTimerMode + birthDate | commit afa3d67 |
| v3-early | v2 + bindings，無 bindingsSeeded | commit d05724a（bindingsSeeded 加欄前） |
| v3-late | v3-early + bindingsSeeded | commit 10284df 後 |

v3-early 與 v3-late 的 schemaVersion 值相同（皆為 3），差異僅在鍵是否存在。這正是「旗標與版本號正交」的具體體現，兩者必須各自成為獨立 fixture——只測其一會漏掉 _migrateBindingSeed 的觸發分支。

fixture 內容須以 git show <commit>:lib/models/settings_model.dart 讀取各版 toJson 實際輸出欄位為準，禁止依 SPEC-009 描述推測。

### 斷言要求

每組 fixture 逐欄位斷言 fromJson 結果，不可只斷言物件非 null 或只抽查部分欄位。必含：

- 每個欄位的值與型別
- bindings 長度（v1/v2 應為空，v3 依 fixture 內容）
- bindingsSeeded 旗標的最終值（注意 W1-011 更正：缺鍵時 fallback 為字面 false，非 defaults 的 true，這是 _migrateBindingSeed 的觸發條件）
