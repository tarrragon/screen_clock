### 現況證據（PM 觀察，代理人須獨立重現）

建立 1.4.0-W1-003 時執行的命令含 --blocked-by 1.4.0-W1-002（該 ID 當時已存在），CLI 未報錯、ticket 建立成功，但：

### 已知程式碼路徑（起點，非結論）

| 位置 | 內容 |
|------|------|
| commands/create.py:1273 | parser.add_argument("--blocked-by", ...)，dest 應為 blocked_by |
| commands/create.py:570 | blocked_by = [b.strip() for b in args.blocked_by.split(",")] if args.blocked_by else [] |
| commands/create.py:626 | config 組裝："blocked_by": blocked_by if blocked_by else None |
| lib/ticket_builder.py:724 | frontmatter 組裝："blockedBy": config.get("blocked_by") or [] |
| commands/create.py:657 | _validate_before_persist 讀 config.get("blocked_by") 做存在性與循環依賴檢查 |

上述路徑表面上完整。SKILL.md 提及 1.0.0-W1-027「三建票路徑共用 ticket_builder」，須確認 create 命令實際走的是哪一條路徑，是否存在另一個 config 組裝點未傳遞此欄位。

### 重現方式建議

在不污染正式 ticket 空間的前提下重現：優先用 pytest 直接呼叫 create 的 config 組裝函式並斷言 blocked_by；若須端對端驗證，建立臨時 ticket 後以 git 還原或直接刪除檔案，並在重現實驗結果章節記錄清理動作。

驗證一律以固定值為準（grep frontmatter 的 blockedBy 行、raw 輸出），不以 CLI 未報錯推斷成功。

### 執行約束

- 修復範圍限 --blocked-by 與 --related-to 兩參數的傳遞路徑，不順手重構 create.py 其他部分
- 既有 set-blocked-by / set-related-to 行為不得改變
- 既有不帶這兩個參數的建票行為不得改變

### 並行安全約束（重要）

本票修改 .claude/skills/ticket/ 下的程式碼，而 ticket CLI 經 shim 即時反映源碼——編輯中的破損狀態會立即影響所有並行執行中的代理人（同批派發的其他 ticket 都會呼叫 ticket track claim / append-log / set-acceptance / complete）。

要求：
- 每次編輯後立即執行 ticket track summary 確認 CLI 仍可運作，不留下語法錯誤或 import 失敗的中間態
- 修改期間禁止重跑 install-skill-clis.py
- 若修改牽涉 create.py 以外的共用模組（如 ticket_builder.py），改動後額外執行 ticket track query 與 ticket track list 確認讀取路徑未受影響
