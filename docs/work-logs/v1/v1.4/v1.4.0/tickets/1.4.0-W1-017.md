### 設計決策

- 降級判準：以「原始值是否存在」區分「欄位缺失」（向後相容正常情境，不記錄）與「欄位型別錯誤」（真降級，記錄 warning）。缺欄位是 schema 演進的預期路徑（v1~v3 fixture 皆大量缺欄），與真正的資料損壞（型別不符）語意不同，混為一談會讓日誌在每次讀取舊版資料時洗版。
- 共用 helper _resolveField<T>：統一 fromJson 12 個純量欄位的 fallback 邏輯（raw/parsed/fallback 三元判斷 + 條件式記錄），取代原本各自展開的 _asXxx(json[k]) ?? d.k。_bindingsFromJson（略過非法條目）與 _asClampedDuration（型別錯誤分支）走獨立路徑但共用 _logFieldTypeError 訊息格式，維持三處日誌文字一致可讀。
- level 900 沿用既有慣例：Context Bundle 註記「900 保留給 error」，但實際查證全專案（cursor_locator_hotkey_controller.dart:130 明確註解「warning 日誌」、cursor_locator.dart、input_binding_channel.dart、fullscreen_detector.dart、method_channel_safety.dart 皆用 level 900 表達 warning/降級語意，settings_model.dart 既有的 _asClampedDuration 非有限值分支亦同）判定 900 = warning 是本專案實際慣例，Context Bundle 該句與現況不符。依 tool-output-trust-rules 規則 6（驗證器/舊註記與建立端現況衝突時以建立端為準）沿用 900，未新增第二個 level 數字造成同檔不一致。
- 可測試性 seam：developer.log 為 dart:developer native/external 實作，無法在 flutter test 內攔截。新增 @visibleForTesting void Function(String) debugSettingsModelLogSink（預設呼叫 developer.log），測試以 setUp/tearDown 覆寫並還原，換取「無日誌輸出」「日誌含欄位名」等斷言的真實驗證力（而非只驗證值行為）。此為本檔首次引入此模式，因應收斂 acceptance 3「正常路徑不輸出日誌」需要真正攔截才能寫成非假綠燈測試（Context Bundle 已預先提醒此風險）。

### 修改檔案

- lib/models/settings_model.dart：新增 debugSettingsModelLogSink、_logFieldTypeError、_resolveField<T>；fromJson 12 個純量欄位改走 _resolveField；_bindingsFromJson 兩個略過分支補日誌；_asClampedDuration 型別錯誤分支補日誌（原本靜默）。
- test/models/settings_model_test.dart：新增群組「SettingsModel fromJson 降級日誌」10 個測試，涵蓋單欄位/多欄位型別錯誤、bindings 兩種略過情境、cursorLocatorEffectDurationSeconds 型別錯誤、三種「不應記錄」情境（全合法/欄位缺失/合法但越界的夾制）、INV-04 不拋例外。既有 golden fixture group（1.4.0-W1-015 產出）未修改內容，僅受既有欄位缺失路徑影響（驗證為零日誌，與其設計相容）。

### Phase 4 重構評估

- 重構需要：否。_resolveField/_logFieldTypeError 均為 4-6 行單一職責函式；fromJson 本體行數成長是因 13 個欄位各自需要顯式欄位名字串以支援日誌，屬結構性必要，非設計缺陷（原本每欄位就已各自一行）。
- 技術債務：無新增。既有的 debugPrint 技術債（main.dart / input_binding_controller.dart）不在本 ticket 範圍，未觸碰。
- 程式碼品質：A（dart analyze 0 issues；日誌慣例與既有檔案一致；新增測試對「有日誌」「無日誌」皆有真實攔截驗證，非只測行為值）。
- 結論：無需重構，維持現狀。
