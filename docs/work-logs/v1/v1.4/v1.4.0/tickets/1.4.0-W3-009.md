校準表全部驗證屬實：reset 合併與 scheduleDeadline 抽取確如 PM 校準所述，比原策略描述的更容易（inout 簽章與 non-optional cancelDeadline 已到位，無需再處理型別分歧）。

抽取項目（對照 how.strategy 五項逐一落地）：

1. resolveTarget() -> (CursorScreenSnapshot, CursorScreenResolution)：play 與 handleFrame 共用的前置三行（取快照/取游標/判定），switch 與對應 log 留在各自呼叫端（兩處對同一判定結果的診斷措辭不同：play 語境「無法播放」、handleFrame 語境「續行播放」，故不合併 switch）。
2. scheduleDeadline(duration:generation:) -> () -> Void：兩處逾時重排重複的共用尾段。世代由呼叫端傳入——startNewPlayback 傳入遞增後的 capturedGeneration，resetExistingPlayback 傳入現有 generation（不遞增），差異在呼叫端顯性，未動既有世代語意。
3. resetExistingPlayback 的搬遷區塊改呼叫既有 updateTargetScreenIfNeeded(_:session:)，消除與 handleFrame 逐字重複的搬遷邏輯。該函式原僅被 handleFrame 呼叫、由 T2.D-03/04/05 間接覆蓋，合併後仍由同一組測試覆蓋 reset 路徑。
4. handleFrame 內螢幕重判定三態 switch 抽為 updateScreenOrEndPlayback(for:) -> Bool：無可用螢幕時走 endPlayback 並回傳 false（呼叫端 guard 後 return，停止該幀後續處理）；命中/退回 main 時視需要搬遷並回傳 true。
5. 淡出計算抽為 static func fadeAlpha(elapsed:duration:) -> CGFloat?：純函式，nil 表示尚未進入淡出窗（呼叫端不設定 alpha，維持既有值）。fadeDuration <= 0（含 duration<=0）與 elapsed 未達 fadeStart 兩種情形統一回傳 nil，與原地實作的 fadeDuration > 0 && elapsed >= fadeStart 守衛語意一致（已由 8 個邊界測試驗證等價）。

硬約束驗證：
- endPlayback 單一出口未動：仍是 stop/handleDeadline/updateScreenOrEndPlayback(.unavailable)/handleFrame(duration 達成) 四條路徑共用的唯一收尾點，函式本體逐字未改。
- generation 在 reset 不遞增：resetExistingPlayback 呼叫 scheduleDeadline(duration:generation: generation)（讀現有值，不 +=1）；startNewPlayback 呼叫 scheduleDeadline(duration:generation: capturedGeneration)（capturedGeneration 來自遞增後的 generation）。1.4.0-W2-041 的世代守護測試全數綠燈。
