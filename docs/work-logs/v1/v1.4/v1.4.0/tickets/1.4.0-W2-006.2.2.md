### 本票的三項工作

1. **production surface 與驅動**（步驟 5）：依 Phase 1 §2.5 十二項屬性契約建立真實 `NSWindow`，顯示採不搶焦點方式；驅動以顯示器垂直同步機制回呼並一律派回 main thread，提供重綁與停止。
2. **錯誤對應檔**（步驟 6，N-1 裁定產物）：新增 `macos/Runner/CursorLocatorErrorMapping.swift`。**不得放進 `CursorLocatorEffectWindow.swift`**——該檔刻意只依賴 AppKit，混入 Flutter 型別會使測試群組 C/D 被迫連帶引入 Flutter 依賴，這是 N-1 裁定的核心理由，亦是 `.2.1` 與本票拆票的依據。
3. **bridge 委派**（步驟 7）：`MainFlutterWindow.swift` **僅改一處**——`CursorLocatorBridge` 的 `handlePlay` 在既有參數解析成功後改為委派至控制器，以錯誤對應單元決定回應。既有參數失敗分支（`invalid_arguments`）完全不動。該檔現為 836 行、已超 cognitive-load 閾值 2.8 倍，不得再增其他職責（拆分屬 `1.4.0-W2-015`）。

### 測試端的反向約束（Phase 2 已指定）

T2.E-05 / E-06 必須以**字串字面**逐字斷言錯誤碼，**不得**引用實作端的錯誤碼列舉。實作者不可為消除重複而讓測試改用同一常數——那會使常數改名時測試同步變動，錯誤碼契約失去鎖定作用。

### 測試群組執行順序（Phase 2 §四指定）

E（6，最小、驗證錯誤對應）→ F（7，真實視窗）。F 需啟動宿主 app，是唯一可能被環境阻擋的群組，放最後可避免環境問題擋住前面所有進度。

### B-7 權限彈窗：已綁 trigger 的條件延後

宿主 app 啟動時 `MainFlutterWindow` 的 CGEventTap 可能彈出輔助使用權限對話框，阻塞無人值守執行。母票 Phase 2 驗收已指定：

- trigger：本票執行 `xcodebuild test` 時**實際觀察到**權限彈窗阻塞
- 承接動作：建立追蹤票處理宿主啟動流程的測試環境隔離
- **禁止**以繞過測試或改寫宿主啟動流程的方式在本票內就地處理（後者屬 `1.4.0-W2-015` 範圍）
- 執行者須於 Test Results **明確回報是否觸發，未觸發亦須寫**

### E_CL_SCREEN 兩條路徑（acceptance 3 的判準）

| 情形 | 行為 |
|------|------|
| 游標落於螢幕排列間隙，退回 main | 僅記 NSLog，**播放照常進行**，`play` 回傳成功 |
| 無任何可用螢幕 | 以 `FlutterError` 回傳且不播放，歸入同一錯誤碼（不新增碼以免擴張 SPEC-008 定義的集合） |

判準：**復原路徑不以 FlutterError 中斷播放**。會到達 Dart 的 E_CL_SCREEN 語意唯一（無可用螢幕）。

**禁止**新增原生至 Dart 的反向 channel 或 EventChannel——「回報 Dart 側」指 `play` 這次 method channel 呼叫以 `result(FlutterError(...))` 回傳，屬同步回應。該做法違反 SPEC-008 介面規格。
